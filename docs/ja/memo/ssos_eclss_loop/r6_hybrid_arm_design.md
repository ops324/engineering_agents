## 何を測るのか — ハイブリッド腕ではなく、判断点ごとの寄与

**ハイブリッド腕がルール腕に勝つのは、ほぼ確実で、面白くない。**
ルール腕の持続性をそのまま持ったうえで判断だけ足すので、悪くなる理由がない。

測るべきは「**LLM をどこに置くと効き、どこに置くと害になるか**」である。
したがって成果物は「ハイブリッド腕は N 点だった」ではなく、**判断点を1つずつ入れ替えた腕の並び**である。

## 測る道具（EXP-016 で確定）

共通3軸（残存50+A20+B20）に **C 判断・D 応答を必ず並記**する。
`~/ea-runs/analysis-tools/compare.py`。物差しは `run 自身の閾値`。

### ★ R6 では共通3軸は使えない見込み — 先に言っておく

乗員数を揃えた22本（v5 の LLM 腕・全員が乗員3）で、各軸がどれだけ動くか:

```
              SD      範囲     満点に対する範囲
共通3軸      0.205    0.766        0.9%     ← 生存が同じなら、ほぼ定数
C 判断       1.116    4.714       94.3%
D 応答       1.445    4.881       97.6%
```

**生存の運を除くと、共通3軸は満点の 0.9% しか動かない。**
ハイブリッド腕は（ルール腕と同じく）乗員4/4を守る見込みなので、
**変種を何本作っても共通3軸では全部同じに見える。**

n=24 での最小検出差（検出力0.8・両側5%）:

```
共通3軸  5.285 / 90        C 判断  0.638 / 5        D 応答  0.869 / 5
```

**結論: R6 の主指標は C・D。共通3軸は「乗員が死んでいないこと」の確認に使う。**

## 判断点の候補（EXP-015 で絞り込み済み）

```
a 優先順位  → **渡さない。ルールで固定**（能力でなく一貫性の問題。EXP-015 で決定済み）
b 要求量    → 候補。**in-sim**（run の中で働く）
c 診断      → R4 が将来フェーズなので測れない
d 設計提案  → 候補。**post-run**（run と run のあいだで働く）。実装済み・一度も測っていない
```

## ★ b と d は同じ実験に入れられない（設計上の分岐点）

当初は {b, d} の 2×2 要因計画を考えたが、**成立しない。**

```
b 要求量    run の中で、毎 step 働く            → 腕の違いとして測る
d 設計提案  run が終わってから、次の run に効く   → 対照実験（before/after）として測る
```

働く時刻も、比較の相手も違う。**2つの実験に分ける。**

## R6a — 要求量を LLM に渡す（in-sim）

### 機構

```
ルールで固定   いつ撃つか（帯を割ったら発火し、回復目標まで続ける）
              何を撃つか（ARS / OGS / WRS の選択＝優先順位。a）
LLM が決める   goal の「量」だけ
```

### ARS では効かない。OGS と WRS だけ（既知）

定格の不変条件により ARS の goal は天井で頭打ちになる（EXP-014 の未解決事項）。
**ARS の挙動は「回す／回さない」の二値**で、CO₂ が 2.1 kg でも 7.9 kg でも同じ。
OGS・WRS は goal が「量」なので効く。

### 腕

```
H0  ルール腕（既存の ref_labeled_rule_base）      n=1（決定的・0秒）
H1  ルール腕 ＋ b（OGS/WRS の量だけ LLM）          n=24（520s/本 = 3.5時間）
```

### 正直に言っておく弱点

**b が効く余地は小さいかもしれない。** B 資源余裕軸は v5 の LLM 24本で SD 0.033（満点の 0.2%）
しか動いていない。要求量の巧拙が現れる先が B だとすれば、**この運用点では測れない可能性がある。**
効くとすれば C の `request_sizing`（満点2・SD 0.536）と D（満点5・SD 1.445）である。

## R6b — 設計提案（post-run）

### 既に実装されていて、全実験で切ってある

```
$ grep design-mode ~/ea-runs/analysis-tools/*.sh
  → 7スクリプト全部が --design-mode none
```

### 機構

```
ea run --design-mode llm   →  LLM が設計提案を出す              ← 判断
ea evaluate                →  提案あり／なしで対照実験、物差しは凍結  ← 決定論
                           →  verdict: improved / refused
```

提案できるのは4種類（`design_proposals.py`）:

```
action_profile   ARS/OGS/WRS の action payload（initial_co2_mass 等）
service_config   サービス設定
set_parameter    パラメータ
graph_rewire     トポロジ（Systems Graph の芽）
```

### 物差しは既に凍結してある

EXP-010 で塞いだ穴（提案が自分の採点閾値を書き換える）は、評価層と発生源の両方で対処済み。
さらに 2026-08-28 に `--yardstick run` のガード（`thresholds_modified`）を足した。
**提案が閾値を動かした run は、自分の閾値で採点されない。**

### 測るもの

腕どうしの点の比較ではなく、**提案そのものの質**である。

```
提案の受理率     improved / (improved + refused)
改善量           evaluate が報告する各指標の delta
不正な提案       検証で弾かれた数（design_proposals の validate）
```

### コスト

**まず1本走らせて何が出るか見る。** design=llm が何を提案するのか、
誰もまだ見ていない。1本の費用は未計測（in-sim の LLM とは別系統・27B @ :8001）。
