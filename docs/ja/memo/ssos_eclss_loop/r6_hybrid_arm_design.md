## 何を測るのか

**「LLM をどこに置くと効き、どこに置くと害になるか」。** ハイブリッド腕そのものの点ではない。

## 測る道具 — C・D をやめ、B の CO₂ に移す

### D は使えない（定数）

`rated_step_capacity` の取りこぼしを直した結果、D は3世代とも 5.000・SD 0 に戻った。
**腕の分離には使えない。** 値が 5.000 から外れたら「新しい制限理由が現れ、
飽和として扱うか誰も決めていない」という警報として読む。

### C は主指標にしない

- 実際の発行指令数との相関が v3 −0.671 / v4 +0.205 / v5 −0.629 と不安定
- 5点のうち1点（`invalid_ops`）は `1 − 拒否数/発行数`＝**スキーマ適合度**
- `headroom = min(1.0, 定格/要求)` なので **過小要求は常に満点**（要求0でも満点）
- **no-op と軌道が完全一致する3本に 0.00〜2.72 の差**をつける
- 配点はこの枝の独断（R3 未決）

**`C.request_sizing` は操作チェック**（LLM に量を触らせたなら、触った証拠）として使い、
成果としては報告しない。

### 主指標は B の CO₂ 側

ルール腕の実測（決定的・0秒）:

```
B 資源余裕 12.2378 / 20
  co2_worst     0.0000 / 4    ← ピーク 2.05 kg（帯 2.0 kg を超えている）
  co2_terminal  0.2378 / 4    ← 終値 1.819 kg
  o2_worst      3.0000 / 3  ┐
  o2_terminal   3.0000 / 3  │ 天井。この運用点では動かない
  water_worst   3.0000 / 3  │
  water_terminal 3.0000 / 3 ┘
```

**7.76点が空いている。**（⚠ **誤り。到達可能なのは 3.03点** — EXP-017。冒頭の告知を見ること）そして:

- **規格に紐づく**（CO₂ は NASA-STD-3001 [V2 6004]／OCHMO-TB-004。枝の独断ではない）
- **「いつ撃つか・いつ止めるか」で動く。**「いくつ頼むか」では動かない（定格で clamp される）
- 生存（50点・文書が定義した唯一の式）と同じ合計の中にある

**副次指標**: 共通3軸（乗員が死んでいないことの確認）、`co2` の曝露積分と最長 critical 連続。

## ★ 判断点を選び直した

第1版の b（要求量）は**捨てる。** GPU 0秒で天井に届くうえ、少なく頼むほど点が上がるため。

```
実測: agents.yaml の古い定数2つ（wrs_goal.urine_volume: 2.0、ogs_goal.input_water_mass: 0.15）を
      定格に直すだけで  C 4.3164 → 5.000  （--set 2つ・LLM 不使用・0秒）
```

代わりに、**B の CO₂ に効き、かつ現在どの腕もやっていない**判断点を採る:

| | 判断点 | なぜ効くか | 現状 |
|---|---|---|---|
| **e** | **いつ止めるか** | `co2_recovery_margin_kg: 0.25` は固定値。B の co2_terminal に直結 | ルールが固定 |
| **f** | **帯を割る前に撃つか** | ピーク 2.05 kg が帯 2.0 を超えている原因そのもの。co2_worst 0/4 の在り処 | どの腕もやらない |
| **g** | **応答から学ぶ** | ルール腕は `limited_by` を読まず、50 step 同じ 2.0 L を要求し続けている | どの腕もやらない |
| **i** | **例外時だけ呼ぶ** | ルールの前提が壊れたときだけ LLM を呼ぶ。呼び出し回数が激減しコストも小さい | 未実装 |

**c（診断）も候補に戻す。** 故障フラグは観測文字列に平文で出ている
（`build_llm_situation` の `ars_failure_enabled=...`）。`inject_failures` は実装済み。
**フラグを観測から隠すだけで診断課題が成立する。R4（リーク・N₂）は要らない。**
第1版の「c は測れない」は過大な保留だった。

## 未解決 — 測る前に決めること

第1版の4つに加え、監査が挙げたもの。**どれも数字を見る前に決める。**

1. **主要評価項目を1つに固定する**（B の co2_worst + co2_terminal を提案）
2. **害の定義と非劣性マージン。** 何が起きたら「ここに置くと害」と結論するか
3. **ハイブリッド腕のノイズ床。** 既存の n=18〜26 は LLM 腕の SD 由来で流用できない
4. **多重比較の扱い**（腕 × 指標）
5. **欠測規則**（全滅 run、parse 失敗、提案ゼロ、ゲート不合格）
6. **物差し**（run / std）と `scoring_bar_modified` が空でない run の扱い
7. **モデルの交絡。** 実務側 `qwen3.5-9b` / think false / 768 tok @ :8000、
   設計側 27B / think true / 16384 tok @ :8001。**置き場所とモデル能力が完全に交絡する**
8. **受理率の定義を実装の語彙で書く。** `_verdict()` が返すのは
   `improved / worse / mixed / no_effect / inconclusive` で、**`refused` は存在しない**
   （第1版の「受理率 = improved/(improved+refused)」は実装に無い。しかも
   その定義だと `worse` が分母から落ち、**害が定義上検出できない指標**になっていた）
9. **提案ゼロの run が評価対象から消える生存者バイアス**（`change_count > 0` のときだけ
   `design_proposals.json` が書かれる）。**最悪の提案ほど外れる**
10. **parse 失敗時にルール提案器へ黙って落ちる**（`decision_source="llm_parse_fail"`）。除外規則
11. **打ち切り条件**と `backup.sh` の実行タイミング、`code_version.dirty` の事前確認

# 第1版が誤っていた理由

記録として残す。**予測が設計を歪めた実例である。**

第1版は「ハイブリッドはほぼ確実に勝つ」と先に書き、そのうえで:

- 主指標を **C・D** に置いた。D は採点の取りこぼしで、C は判断を測っている証拠が無かった
- 判断点を **b（要求量）** にした。それは 0秒で天井に届く変数で、
  しかも `headroom = min(1.0, 定格/要求)` により**少なく頼むほど点が上がる**
- 「少なく頼む」害は共通3軸に映らない（定格の clamp で過大要求は物理的に不活性、
  OGS・WRS を全部止めても O₂ は約1.8 kg・水は約4 L しか動かず帯に届かない）

**つまり、設計どおり走らせれば予測どおり「ハイブリッドが勝った」が出て、
その勝ちは判断の質と無関係だった。** 最も高得点を取る戦略が最も工学的に悪い戦略、
という形の Goodhart になっていた。

**そして基準線（H0'）とプラセボ（H0''）を置いていなかった** — 負ける可能性を潰す方向の欠落である。

支払った代償は**トークンのみ。GPU は0秒**。監査を測定前に入れたことで 3.5時間を捨てずに済んだ。
