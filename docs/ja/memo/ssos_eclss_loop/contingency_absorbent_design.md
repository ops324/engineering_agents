## なぜ要るか — 6回の失敗が同じことを言っている

**[EXP-038](../experiments/EXP-038-the-situation-decides-not-the-response.md) が壁を数字にした:**

```
状況の効果（通常 → WRS 故障）   **50.25点**
応答の効果（故障下で最善を選ぶ） **0.21点**
⇒ 状況の効果は応答の効果の **234倍**。結果を決めるのは状況であって応答ではない
```

**判断が生まれるには、応答が結果を決める必要がある。** いまの模型には**手当てが無い**ので、
故障が起きた時点で結末が確定する。ROADMAP が R4 で既に書いていた
「リークだけを入れてはいけない。**対処手段とセットでなければ実験にならない**」の実測確認である。

## ★ 先行設計との関係 — [repair_and_diagnosis_design.md](repair_and_diagnosis_design.md) は同じ壁で落ちている

**同じ問題に対する先行設計が既にあり、EXP-019 で落ちている。** 必ず先に読むこと。

```
先行設計（案4）   A 何が壊れたかを隠す ＋ B 修理に時間の代償を与える
落ちた理由        **診断に曖昧さが無い。** ARS の故障署名は 1 step で −0.0047 対 +0.0578 の
                12倍差・ゆらぎゼロ。**隠しても引き算1回で分かる**
                ⇒ 診断が判断にならず、「すぐ直す」が厳密に支配的になる
```

**本設計が同じ落ち方をしない理由（ここが分かれ目）:**

```
先行設計は判断を「**診断**」に置いた  → 「何が壊れたか」が分かってしまえば判断は消える
本設計は判断を「**配分**」に置く      → 「何が壊れたか」が完全に分かっていても判断は残る

  不確かにすべきは「何が壊れたか」ではなく「**この先どれだけ続くか／あと何回来るか**」。
  故障がいま起きていることは見えてよい。**見えないのは未来である。**
  ⇒ EXP-019 の「引き算1回で分かる」は、**現在**の推定であって**未来**の推定ではない
```

**⚠ 著者の手順違反:** この設計は `repair_and_diagnosis_design.md` を**読む前に**書いた。
同じディレクトリにあり、ファイル名で分かる位置にあった。**今日4回避けてきた失敗の型である。**
読んだ結果、設計は変わらなかったが、**条件C の言い方は上のとおり書き直した。**

## 提案 — 有限の消耗品吸収剤（LiOH 相当）

**実機の輪郭に合わせる**（ユーザー指示「ARS の異常時は将来的に実機と同じように」）。
一般に、この種の装置は「同じ機体を強く回す」のではなく
**冗長系 / 消耗品 / 代謝負荷の低減**で対処する。ここでは**消耗品**を採る — 最も単純で、
条件 A〜D を構造的に満たすため。

```
新しい状態   consumable_absorbent_kg   初期在庫（有限・補給なし）
新しい指令   use_absorbent {"amount": <kg>}
効果        投入 1 kg あたり co2_removal_per_kg だけキャビン CO₂ を除去。**在庫は戻らない**
```

### 6条件をどう満たすか

```
A 費用      在庫が減る。**補給が無いので、使った分は永久に失われる**
B 別の使い道 故障は run 中に**複数回**起きる。早く使い切ると、次の故障で手当てが無い
C 曖昧さ    ★ **故障が「いま」起きていることは見せてよい。見せないのは「この先」である。**
           継続時間と次の故障までの間隔は seed から決まる（＝run は決定的で再現できる）が、
           観測には出さない。「すぐ戻るなら温存すべき／戻らないなら今使うべき」が事前に分からない。
           **EXP-019 が落ちた「引き算1回で現在が分かる」は、この条件を壊さない**
D 使いすぎの罰 在庫が尽きた後に故障が来ると、手当てゼロで乗員を失う
E 窓        判定は必ず**窓を倍にして**確かめる（EXP-037 の規則）
F 効果の大きさ 吸収剤が乗員を救えるなら、応答の効果は**最大 50点**（残存軸）。
           状況の効果と同オーダーになる ← **これが 234倍を壊す唯一の道**
```

## 事前登録（実装前にここで固定する）

### 主指標
```
共通3軸（90点満点・連続量）。**生存者数を主指標にしない**（0〜4 の5段階で差を丸め落とす）
```

### 判定規則
```
成立   ①**状況を見ない定数**（常に使う / 常に温存 / 固定量）を、**状況依存の政策が上回る**
      ②その差が**応答の効果**として 1点以上（EXP-038 の 0.21点を明確に超える）
      ③**窓を倍にしても①②が生き残る**
不成立 上のどれか1つでも満たさなければ、この設計は落とす
```

### ★ 撤回条件（発火しうる入力が実在するか、実装前に確認すること）
```
撤回1  **単一の定数が全状況で最適** → 落とす。EXP-027/030/038 と同じ結末
       （発火しうるか: 定数腕を並走させれば判定できる。**実装前に確認する**）
撤回2  故障の継続時間が観測から**推定できてしまう**（例: 他の telemetry で分かる）
       → 条件C が満たされず落とす
撤回3  吸収剤の在庫を増やすと**常に良くなる**（単調） → 条件D が無い。落とす
撤回4  乗員が救えない（吸収剤の定格が足りない） → 条件F が無い。落とす
撤回5  窓を倍にして結論が変わる → 落とす（EXP-037 の規則）
```

### 予測（実装前に書く）
```
P1  定数「常に使う」は在庫を早く使い切り、**2回目の故障で乗員を失う**
P2  定数「常に温存」は1回目の故障で乗員を失う
P3  したがって内点が出る。**ただし過去5回すべてで同じ予測が外れている**ので、
    P1・P2 が両方外れる（＝どちらかの定数が勝つ）確率は低くない
```

## ★ 自己申告する弱点（監査官はここを避けて撃つこと）

```
1  **条件C の実装が最も脆い。** 未来を隠すつもりでも、故障の長さが**常に同じ**なら
   1回目の run で学習でき、2回目以降は既知になる。**長さと間隔に分布が要る。**
   そして分布を著者が選ぶ以上、**著者が難易度を作れてしまう**（弱点4 と同根）
2  **条件Fは仮定であって測定ではない。** 「吸収剤が乗員を救える」定格を選べば満たせるが、
   それは**答えを先に決めて定格を逆算する**ことになりかねない。物理的な出典が要る
3  **6条件を満たす設計は、判断が生まれるように作った設計**である。
   「作れば生まれる」のは当たり前で、**面白いかどうかは別**（EXP-025 第1版が落ちた型）
4  複数回の故障は**シナリオの選択**であって物理ではない。頻度と間隔を著者が選ぶ以上、
   **著者が内点を作れてしまう**。頻度は出典か、少なくとも事前登録で固定すること
5  この文書は**実装前の設計であり、S1（定数で解けないか）を実測していない**。
   撤回1 の確認は実装前に行うと書いたが、**吸収剤が無い状態では確認できない**。
   ⇒ **最小実装を先に作り、定数腕を並走させてから本設計に進むのが正しい順序かもしれない**
```
