# R2 — 酸素をキャビン大気にする（実装前の設計）

2026-08-28。**未実装。** [ROADMAP](../experiments/ROADMAP.md) の R2。
先行文書 [o2_cabin_atmosphere_scoping.md](o2_cabin_atmosphere_scoping.md) の見積もりを、
一次資料の数値で置き換えたもの。**リークは含めない**（R4 に分離済み）。

## なぜ直すか — これは誤りの訂正である

```
388 m³ のキャビンを正常酸素に保つには 105〜112 kg 必要
現行のタンク全量は 8 kg  → キャビン換算で 11.9 mmHg = 窒息水準
```

**物理的にありえない値**である。そして仕組みは正しく動くほど、この土台の上で
確信を持って間違える。EXP-014 の全滅4本（`request_o2` による O₂ 死）は
**8 kg という誤設定が生んだ人工的な死**であり、正しい物理では起きない。

## 一次資料 — [V2 6003] は ppO₂ ではなく PIO2 で規定されている

NASA-STD-3001 Volume 2 Rev D、Table 6.2-1 より（規格本体から直接読んだ）:

```
PIO2 = (PB - 47) x FIO2
   PB   = 周囲気圧 (mmHg)
   FIO2 = 乾燥気体としての O2 モル分率
   47   = 肺内の水蒸気分圧 (mmHg)

  正常酸素 目標帯          145-155 mmHg   (2.80-3.00 psia)   無期限
  無期限 高酸素 上限        356 mmHg       (6.89 psia)        無期限
  短期 高酸素 上限          791 mmHg       (15.30 psia)       6-9時間
  軽度低酸素 下限           127 mmHg       (2.46 psia)        監視付きで無期限
                          （1時間平均。絶対下限 122 mmHg / 2.36 psia）
```

**ppO₂（乾燥分圧）ではない。** 湿度を考慮した吸入分圧である。
`[V2 6004]`（CO₂）が乾燥分圧なのと対照的で、**同じ扱いにはできない。**

### 総圧 760 mmHg 一定と仮定した場合の換算

```
ppO2 = PIO2 x 1.0659

  正常酸素 下限 145 → ppO2 154.6 mmHg → キャビン O2 105.0 kg
  正常酸素 上限 155 → ppO2 165.2 mmHg → キャビン O2 112.2 kg
  軽度低酸素 下限 127 → ppO2 135.4 mmHg → キャビン O2  91.9 kg
  絶対下限     122 → ppO2 130.0 mmHg → キャビン O2  88.3 kg
```

**この仮定は R2 では成立する**（リークが無いので総圧は動かない）。
R4 でリークを入れると総圧が動くので、そこで N₂ が要る。**R2 には要らない。**

## 決定（2026-08-28）

```
① 供給とキャビンの境界   A — OGS はキャビンへ直接吐く。供給タンクは無くなる
   ただし request_o2 は残す（下記）
② 初期値                105.58 kg（PIO2 145.8）。正常酸素帯の下端すぐ上から始める
③ 帯を割ったときの減員   B — O₂ では減員させない。規格違反は採点にだけ出る
```

### ① の但し書き — `request_o2` は消さない

当初「A を採れば `request_o2` が消える」と整理したが、**誤りだった。**
2つの別のことを混同していた:

```
(1) OGS の出力がどこへ行くか        ← 論点①
(2) request_o2 サービスが存在するか  ← 別の話
```

`request_o2` は **SSOS の実インターフェース**である:

```
ros2/topics.py   SERVICE_OGS_REQUEST_O2 = "/ogs/request_o2"
backend.py       def request_o2(self, amount) -> ServiceResult: ...   ← 抽象契約
```

参照は20ファイル（ROS2 ブリッジ・mock backend・One Piece クライアント・ダッシュボード）。
**消すと backend 差し替えの契約が壊れる。** このプロジェクトが SSOS に繋ぐ前提で
作られている以上、消してはいけない。

**残す。引き出し元がキャビン大気になる。** 実機の `/ogs/request_o2` は
「O₂ を消費者に引き渡す」サービスで、ペイロード供給や EVA スーツ充填など
キャビンから酸素を持ち出す正当な操作である。

帰結: EXP-014 の全滅4本の原因は**消えないが、桁違いに軽くなる**。

```
現行    タンク 8 kg から引き出す        → 3回で全滅しうる
修正後  キャビン 105.58 kg から引き出す  → 全滅には 100 kg 超の引き出しが要る
        ただし 0.61 kg 引けば正常酸素帯は割る（規格違反として採点に出る）
```

レバーは残り、結果が「死」から「規格違反」に変わる。③B と整合する。

### ② の根拠 — 窓が狭いので、下端近くから始めるしかない

```
正常酸素帯の幅   7.2 kg
50 step の消費   2.34 kg   ← 帯の 1/3 しか動けない
```

観測窓内に 145 mmHg を割らせるには、**開始値を下限から 2.34 kg 以内**に置く以外にない。
**意図的なシナリオ設計である。** ただし既存の CO₂ も同じ作り（1.3 kg / 閾値 2.0 = 65% の位置）
なので、設計言語としては一貫している。

```
何もしない  → step 13 で 145 mmHg を割り、50 step 後 103.24 kg（PIO2 142.6）規格帯の外
OGS を回す  → 50 step 後 109.67 kg（PIO2 151.5）帯の中央付近まで回復
```

**放置すれば違反し、動かせば回復する。** そして2資源を違う頻度で管理する必要が出る:

```
CO₂ を維持するのに ARS 37/50 step
O₂ を維持するのに OGS 18/50 step   → 合計 55 発行 / 50 step
```

いままで CO₂ しか生きた軸が無く「持続性」だけを測っていたが、**優先順位づけ**が測れるようになる。

### ③ の根拠 — 規格が「割っても死なない」と言っている

145〜127 mmHg は表に **"Mild Hypoxia ... Indefinite with monitoring"** と明記されている。
**割ったからといって人は死なない。** 減員の根拠になるのは 127 mmHg（絶対下限 122）だが、
そこまで落ちるには93時間かかり、50 step では届かない。

```
規格違反（145 mmHg 割れ）→ 観測窓内に起こる。採点に出る
致死（127 mmHg 割れ）    → 50 step では起こらない。R4 のリークで初めて起こる
```

**「規格を割ること」と「死ぬこと」を分ける**のが規格に忠実な読み方であり、
CO₂ 側も同じ構造（[V2 6004] 超過と減員は別判定）になっている。

## 判断が要った点（記録）

### ① 供給とキャビンの境界

OGS が作った O₂ はどこへ行くか。

| 案 | 挙動 | 帰結 |
|---|---|---|
| **A. キャビンへ直接** | OGS → `cabin_o2_kg`。タンクは無くなる | 単純。ただし `request_o2`（在庫から引き出す）の意味が消える |
| **B. タンク経由、手動放出** | OGS → タンク → 放出コマンドでキャビンへ | 操作が1つ増える。**判断の対象も増える** |
| **C. タンク経由、自動補給** | ppO₂ が下限を割ると自動でタンクから補う | 実機に近い。ただし**自動化した部分は腕の判断から外れる** |

**この選択が、シナリオが何を問うかを決める。**
現行の `request_o2` は「在庫から引き出す」サービスで、EXP-014 の全滅4本の原因だった。
A を採ると**このレバー自体が消え、あの失敗モードは二度と起きない**。

### ② 正常酸素帯のどこを初期値にするか

帯の幅は 105.0〜112.2 kg（7.2 kg）で、**乗員4の消費 3.36 kg/day では上端から下端まで 51.7 時間**。
観測窓 16.7時間で消費されるのは 2.34 kg。

```
初期値を上端 112.2 kg にすると  →  16.7時間後も 109.9 kg。帯の中に留まる
初期値を下端 105.0 kg にすると  →  16.7時間後は 102.7 kg。帯を割る（PIO2 141.9 mmHg）
```

**下端から始めれば、何もしなければ観測窓内に規格違反へ落ちる。**
上端から始めれば、O₂ は 50 step のあいだ完全に不活性になる。

### ③ ★ 新しく判明した論点 — 帯を割ったときに乗員を失わせるか

現行のサバイバル規則は `o2_storage_low_kg: 6.0` という**タンク在庫の閾値**で減員を決めている。
キャビン大気にすると、この 6.0 kg には意味が無くなる。

| 案 | 帰結 |
|---|---|
| **A. 規格の帯を減員の根拠にする**（PIO2 127 mmHg 未満が続いたら失う） | 規格と減員が一致する。ただし**帯を割るのに 93 時間**かかるので、50 step では起きない |
| **B. O₂ では減員させない**（規格違反は採点にだけ出る） | **O₂ は「正しいが人を殺さない軸」になる。** CO₂ だけが致死になる |
| **C. 観測窓を延ばす**（50 step → 300 step 以上） | O₂ が生きた軸になるが、**LLM の実行時間が6倍**（1 run 8分 → 50分） |

**B を推す。** A は 50 step では発火せず、C は測定コストが現実的でない。
そして R4 でリークを入れれば、O₂ は**リーク経由で**致死になる。
**O₂ が人を殺す経路はリークであるべきで、代謝ではない** — 108 kg の在庫に対し
乗員4の消費は 32日ぶんであり、代謝で酸素が尽きるシナリオは現実的でない。

```
規格に紐づいた軸   CO₂ ✅  水 ✅  O₂ ✅  → **3/3**
ea score の "not scored against a standard"  → **0行**（habitat 指定時）
物理ゲート  pass 9/9
テスト  606 passed / 0 failed
```

### 決定的な腕の分離（設計どおり）

| | no-op | ルール腕 |
|---|---|---|
| 正常酸素帯を割った step | **36/50**（連続36） | **14/50**（連続1） |
| 曝露量 | 23.58 kg·steps | 0.34 kg·steps |
| 終了時 PIO2 | 143.2 mmHg（帯の外） | 145.0 mmHg（帯の際） |
| 軽度低酸素（致死域） | 0 step | 0 step |
| 乗員 | 3/4 | **4/4** |

**規格違反は起きるが、O₂ では誰も死なない。** ③B のとおり。
no-op が乗員を1人失っているのは CO₂ 側の warning dwell による。

### 実装中に判明した訂正

**リポジトリの正準温度は 295.15 K（22℃）** で、設計段階の手計算（293.15 K）と 0.7% ずれていた。
`Habitat` の既定に合わせて全数値を取り直した。

```
              手計算(20℃)   正準(22℃)
正常酸素 下限    104.97 kg  →  104.25 kg
軽度低酸素 下限   91.94 kg  →   91.31 kg
絶対下限         88.31 kg  →   87.71 kg
初期値          105.58 kg  →  104.86 kg (PIO2 145.8)
```

**閾値は `reference_limits.o2_kg_for_pio2` と歩調を合わせること。** 片方だけ動かすと、
プラントの運用点と採点基準が静かにずれる。

## 完成の定義

- `ea score` から `not scored against a standard: o2` が消え、Table 6.2-1 の帯で採点される

- テストが緑（差分で確認）
- ルール腕が生存できる運用点である
