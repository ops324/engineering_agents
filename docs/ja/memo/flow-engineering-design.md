## 目的

ハードウェア要件と変更管理のプロセスを、**AI とグラフデータベースで可視化・構造化**し、
エンジニアの協働を効率化する。**ECLSS はその舞台（＝フローの計測器）であって、製品ではない。**

方式:
- **流れ（順序・条件分岐）は決定的なプログラムで固定する**
- **知的な判断（起草・判定・要約・ルーティング）に LLM を置く**

---

## ★ このセッション自体が、その方式の実例だった

2026-08-29 の作業は、実際にこの形で進んだ:

```
変更提案 → 測定 → 独立監査（3レンズ並列） → 著者による再現 → 人間の判断 → 実装 → 記録と波及
```

**流れは固定で、判断の中身だけが LLM。結果として7回の誤りを捕まえ、うち4回は公開前に止まった。**
**⚠ この「7回」はスコープ内の分子であり、見逃しは未測定（EXP-036）。**

## 1. 実測が確定させた設計原則（本日のデータ）

### ① LLM は「持続」に向かない（EXP-034）

```
ARS を実際に効かせた step 数   ルール腕 37 / LLM 中央値 **8.5**（50 step 中）
時間プロファイル              ルール腕 0/7/10/10/10（始めたら止まらない）
                            LLM     1.0/2.2/1.6/1.9/2.5（全域で薄く散らばる）
```

**⇒ LLM には「一回で終わる判断」だけを与える。ループ・再試行・追跡は決定的側が持つ。**

### ② 「いつやるか」は LLM の仕事ではない（EXP-034）

```
効いていたのは「step13 までに撃ったか」の**二値**。定数なら step0 から撃てる
早撃ち群の最終生存は 2.70 で、**3群中いちばん悪い**
```

**⇒ 閾値・タイミング・トリガは決定的側。LLM は「何を」「なぜ」の側。**

### ③ 行動集合を絞らないと罠を踏む（EXP-033）

```
request_o2 は「酸素を要求」という名前で、実体はキャビンから酸素を捨てるだけ
ルール腕はコード上そもそも出せない。プロンプトは LLM にだけ提示していた
13本が使い、O2 が原因の死は 8.8倍
```

**⇒ LLM に見せる行動集合は、決定的側がホワイトリストで持つ。プロンプトに列挙しない。**

## 2. 決定的フロー（ステートマシン）— 本日、経験的に発見された形

**各ゲートは通らないと次に進めない。**

```
S0  変更要求が入る
S1  ★関門1: 定数で解けないか            → 解けるなら却下（本日3回ここで止まった）
S2  ★関門2: 既存記録に答えが無いか      → **本日3回破った。ここを機械化する**
S3  事前登録（予測・判定規則・撤回条件）  → 測定より前であることを時刻で強制
S4  測定                              → 安い順（決定的 → 再採点 → LLM）
S5  ★関門3: 撤回条件の照合            → 発火したら S3 へ戻る
S6  ★独立監査（複数レンズ・並列・互いの結論を見せない）
S7  著者による再現                     → 監査を鵜呑みにしない
S8  人間の判断                        ← **自動化しない**
S9  実装
S10 記録と波及                        → この変更が古くする文書を探して直す
```

**本日効いたゲート: S1・S3・S5・S6・S7。**
**S2 だけが「文書に書いた規律」で、だから3回破られた。**

## 3. LLM を置くノード / 置かないノード

| ノード | LLM | 理由 |
|---|---|---|
| S1 定数チェックの**設計** | ✅ | 「この任務は定数で解けるか」の問いを立てるのは知的作業 |
| S1 の**判定** | ❌ | 掃引して数字で決まる |
| S2 既存記録の**照会** | ❌ | グラフへのクエリ |
| S2 の**該当判断** | ✅ | 「これは同じ主張か」の意味判定 |
| S3 事前登録の**起草** | ✅ | 本日いちばん価値があった |
| S5 撤回条件の**照合** | ❌ | 事前に書いた規則の機械適用 |
| S6 **監査** | ✅✅ | **本丸。7回の誤りを捕まえた — ただし「ブリーフがスコープに入れた文書の中で」（EXP-036）** |
| S7 **再現** | ❌ | コマンドを走らせる |
| S10 **波及先の探索** | ✅ | ルーティング |

**監査は「複数レンズ・並列・互いを知らせない」で運用する。**
本日は VERIFY（数字の再導出）/ BREAK（結論を壊す）/ DESIGN（設計の妥当性）の3つ。
**3体が別々の欠陥を見つけた。** 各レンズの指示に**その回の偏りの向きを明示する**のが効いた。

## 4. グラフDB — 本日の最大の失敗を機械で防ぐ

**⚠ EXP-035 の測定は、この節について何も言っていない**（腕3 未測定）。
そして安い腕（数値 grep・TF-IDF）は、**3回のうち最も難しい1回を取り逃した** —
初稿と既出先が数値も語彙も共有せず、**意味だけが同じ**だった件である。
**それは下の表が「該当判断」として LLM に割り当てた仕事そのものだが、n=1 では何も言えない。**

**本日3回繰り返したのは「既に記録されていることの再発見」。グラフの第一の仕事はこれ。**

### ノード

```
Claim（主張）       「LLM は no-op と区別できない」  ← **撤回済み。だから例として適切**
Measurement（測定）  run 群・digest・数字
Artifact（成果物）   EXP文書・コミット・README・設定ファイル
Decision（判断）     人間が決めたこと（乗員4・帯の分離・窓50）
Condition（撤回条件） 事前登録した規則
Instrument（計器）   ガード・採点軸・指標
```

### エッジ

```
Claim --supported_by--> Measurement
Claim --refutes / supersedes--> Claim      ← **本日欲しかったもの**
Claim --obsoletes--> Artifact              ← S10 の波及探索
Measurement --produced_by--> Commit
Condition --fired_on--> Measurement
Decision --constrains--> Claim
Instrument --measures--> Claim
Instrument --known_hole--> Claim           ← ガードの穴10件はここ
```

### 決め手になるクエリ

```
S2 のゲート:   同じ測定に既に主張があるか
S10 の波及:    この主張が古くする成果物
健全性:        撤回された主張が、まだ引用されていないか
```

**ハードウェア要件・変更管理に写すと**: Claim → 要件、Measurement → 検証結果、
Artifact → 図面/仕様書、Decision → 設計判断、Instrument → 検証手段。**構造は同じ。**

## 5. 再帰的な自律改善 — 本日わかった危険が、そのまま設計要件

**本日、規律は自然に生まれた**（失敗するたびに1つずつ）:

```
事前登録する → 撤回条件も書く → 全集合に当てる → 定数で解けないか先に見る
→ 窓の曲線を併記する → 既存記録を先に grep する
```

### ★ ただし決定的な失敗モードが1つ

**「既存記録を先に grep する」という規律を本日書き、書いた当日に3回破った。**

```
❌ 学んだ規律 → 文書に追記 → 次回読む       （本日3回破った）
✅ 学んだ規律 → **ステートマシンのゲートに変換** → 通らないと進めない
```

### 再帰の階層

```
レベル1  実行の改善      フローが個別の変更を捌く（本日やったこと）
レベル2  規律の生成      失敗からゲートの候補を作る（本日、自然に起きた）
レベル3  ゲートへの昇格  人間が承認し、ステートマシンに組み込む ← **自動化しない**
レベル4  ゲートの棚卸し  発火しないゲートを検出して削る
```

**レベル3 を人間の承認にする理由**: 本日、著者は自分の判断で
**「設計判断を見落としと呼ぶ」誤りを2回**した（OGS ラッチ / 3.03点）。
**システムが自分でゲートを増やすと、間違ったゲートが増える。**

### ★ レベル3 の昇格を1件、人間が承認した（2026-08-30）

```
昇格したもの  監査スキルの「**その回の偏りの向きの明示**」を必須項目にする
             （`~/.claude/skills/pre-measurement-audit` v1.1.0）
承認          **人間が承認した**（2026-08-30）。これがレベル3 の運用の1件目
賛成の根拠     08-28・08-29 の2回とも、向きを明示した回は監査3体が**別々の**欠陥を見つけた
承知した上の危険 n=2。そして「向きを明示する」ことが監査官を著者の想定内に誘導しうる
             （08-29 の DESIGN は指示の外側を突いたので実害は未観測。**観測を続ける**）
取り消し       1行。SKILL.md の該当箇所を消すだけ
棚卸し（レベル4）**このゲートが発火しなくなったら削る。** 判定材料は
             「向きを明示した回に、3体が別々の欠陥を見つけ続けているか」
```

## 6. ECLSS の役割

**変更管理の領域には普通「正解」が無い。** 提案が良かったかは何年も分からない。
**ECLSS には物理という正解がある。** だから:

```
フローが誤りを捕まえたか  → **まだ検証できていない**。7回は分子で、見逃しの分母が無い（EXP-036）
LLM の判断が正しかったか  → 検証できる（数字が出る）
規律が効いたか           → 検証できる（撤回条件が発火した回数）
```

**ECLSS は製品ではなく、フローの計測器である。**
