# 第1部 — EXP-020 の結論を撤回する

## 撤回1: 「分解能は深さではなく時間にある」は**逆だった**

EXP-020 は「式が深さしか測らないので、時間で測る項が要る」と書いた。**誤りである。**
v5 の 26 run で自分で計算した:

```
                          相異なる値    幅        全滅run(乗員0/4)の順位   生存との相関
現行（帯 91.31・深さ）        3 通り   0.175点            —                  —
帯を揃える（104.25・深さ）   18 通り   1.059点     26本中 最下位（正）      +0.924
時間（帯下滞在割合）          12 通り      —      26本中 下から17位（誤）    +0.131
```

**深さの式は壊れていなかった。見ていた帯が違っただけである。**
そして提案しようとした「時間」の項は、**深さより分解能が低く、生存をほとんど追わない。**

## 撤回2: 時間で測ると**乗員が死ぬと点が上がる**

決定的な反証。**呼吸する人が減れば O₂ の減りが遅くなり、帯を割る回数が減る。**

```
EXP-019 の決定的 60 run   corr(帯下 step 数, 生存乗員数) = +0.202  （＝死ぬほど良い点）
v5 の llm_r23（乗員 0/4・O₂ 最小 89.09 kg・致死帯を 15 step 割った全滅 run）
  時間で測ると  下から17位（no-op より上）
  深さで測ると  最下位（正しい）
```

**[EXP-010](EXP-010-crew-axis-is-not-guarded.md) が塞いだ「死者が消える」穴と同じ形である。**

## 撤回3: 提案指標は OGS 指令数と**恒等式**だった

EXP-016 の C 軸は発行指令数と r=−0.629 で失格になった。同じ検査（W4 で「やっていない」と
自認したもの）を監査が実行した:

```
v5 LLM 24本      corr(帯下 step 数, 総発行指令数) = −0.584   （EXP-016 の失格線と同等）
EXP-019 60本     帯下 step 数 == OGS 発行回数 が 60本中 50本で **整数として完全一致**
```

理由はコードに露出していた。**腕の OGS 発火トリガー `policy.o2_storage_low_kg` と、
提案していた採点帯 `thresholds.o2_storage_low_kg` は同じ 104.25 である。**
`longest_streak_below = 1` なので、帯を割った step 数＝トリガーが鳴った回数＝撃った回数になる。

**採点の帯を、採点される腕の引き金と同じキーに置こうとしていた。**

## 訂正4: 算術が 1項落ちていた

```
                     A.o2      B.o2_worst   B.o2_terminal      合計
EXP-020 が報告          ○           ○         **落とした**     0.0705
正しい                0.0235      0.0470        0.0481        0.1186
```

**私の値は 41% の過小であり、誤りの向きは「帯を揃えるだけでは足りない、だから時間の項も要る」
という誤った結論を有利にする方向だった。**

## 訂正5: 「n=4」は O₂ については n=2 だった

```
base と noWRS       O₂ 系列が**バイト一致**（WRS は O₂ に影響しない）
noWRS_noOGS と noop  帯下 step 数はどちらも 36 で**時間では区別できない**
```

**W5（「軌跡が同一の run を分離していないか」）は「未検証」ではなく、実際に起きていた。**
`--seed` も決定的な腕には効かない（seed 101/202/999 の telemetry がバイト一致・記録専用）。

## 生き残ったもの

**「捨てられている分解能がある」という観察自体は正しい。** 帯を揃えるだけで 3値 → 18値、
幅 0.175 → 1.059点。**ただし直し方が間違っていた。**

## 破れ1（★最重要）— `plant_sim.survival` の滞留表が無防備。**3度目の「1フィールド隣」**

ガード `_scoring_bar_modified`（`scenario_run.py:253`）が見るのは

`warning_loss` / `critical_loss` / `warning_divisor` / `critical_divisor` は**見ていない**。
`*_loss=0` と `divisor=99999` は `enabled: false` と同じ効果を持つ。


**EXP-010 が閉じた穴が、`bands` の隣で開いている。**

## 破れ2 — 既定の採点経路 `--yardstick standard` がガードを一度も呼ばない

`score.py:401` の `_bar_moved_by` 呼び出しは `if yardstick == "run":` の中だけにある。
`--yardstick` の既定は `standard`。

```
帯を動かした run を  --yardstick run      → 正しく拒否
                     --yardstick standard → **93.7点で素通り（警告なし）**
```

**しかも拒否メッセージが「`--yardstick standard` で採点しろ」と案内する。
名指しで案内される避難経路が、ガードの無い経路である。**

## 破れ3 — 何もしない腕が満点 90.000 を取れる

```
--actor-mode none
--set simulation.initial_co2_storage_kg=0.0
--set plant_sim.crew.activity_factor=0.0
--set simulation.initial_o2_storage_kg=200.0
--set simulation.initial_product_water_l=500.0
→ 共通3軸 90.000 / 90（残存 50 / A 20 / B 20）、乗員 4/4、ガード []
```

**ルール腕の公表値 82.230 を 7.77点上回る。** 使ったキーは4つとも監視外。
`plant_sim.crew.activity_factor=0.0` 単独でも 82.2297 → 84.8000（+2.57）。

## 破れ4 — `--habitat-volume-m3` は採点時に物差しを動かせる（構造上ガード不能）

run を1本も走らせ直さずに、`base` の共通3軸が 84.348（388 m³）→ 89.978（100000 m³）。
ガードは「最初の step の前に決まる記録」なので、**事後の指定は原理的に捕捉できない。**

## 破れ5 — ガードは証拠ではなく自己申告

`_bar_moved_by` は `summary.json` の1フィールドを無検証で信じる。
そして `scorecard.json` には**そのフィールドが存在しない**（採点成果物から消える）。

## 副産物のバグ — C 軸 latency の分母が常に既定値

`scorecard.py` の `dwell_steps` は `summary["plant_sim"]…co2.warning_steps` を読むが、
**`scenario_run.py` は `plant_sim` を summary に一度も書かない**（実測 `None`）。
docstring の「anchored on the dwell window that kills」は実装されていない。
