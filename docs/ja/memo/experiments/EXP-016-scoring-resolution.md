## 目的

R6（ハイブリッド腕）を作る前に、**判断の質を測れる物差しが手元にあるか**を確かめる。

EXP-015 で「判断がほとんど点にならない」（ARS 20回以上出しても 0.8点）と分かった。
このままハイブリッド腕を24本走らせても、判断点ごとの寄与は測れない。
**3.5時間を払う前に、無料で確かめられることを確かめる。**

## 1. 公表値の物差しは、CLI からは出せない

採点には物差しが二つある。

```python
score_run(run_dir, habitat=None)              # run 自身の閾値
score_run(run_dir, habitat=SCENARIO_HABITAT)  # NASA-STD-3001 388 m3
```

同じ run が **82.230 と 84.35** の両方になる。EXP-013 が「他の実験と比べるときは
物差しを揃えること（EXP-014 で一度取り違えた）」と書いているのはこれである。

**問題**: `ea scorecard` は `habitat_volume_m3` を渡さないと `SCENARIO_HABITAT` を使う。
つまり **`ea scorecard` からは `run 自身の閾値` を出せない。**
EXP-013〜015 の見出し数字は、その都度 Python を手書きして出していた。

```
ea scorecard ref_labeled_rule_base            → 84.35（std）
ea scorecard ... --habitat-volume-m3 388      → 84.35（既定と同じ。388 が既定値）
score_run(dir, habitat=None)                  → 82.230（公表値）
```

**再現できない見出し数字は、記録として弱い。** telemetry を捨てなかったのと同じ理由で、
物差しも道具の側に固定する。→ `~/ea-runs/analysis-tools/compare.py`（下記）。

### 追記 — CLI に `--yardstick` を足した（ガード付き）

```bash
ea scorecard <run>                      # standard（既定・従来どおり）
ea scorecard <run> --yardstick run      # run 自身の閾値（EXP-013〜016 の公表値）
```

**無条件には足していない。** `_build_yardstick` の実装コメントが理由を書いている:

> Scoring a run against thresholds read out of that same run is the one thing this
> must not do: `--apply-proposals` can write four `thresholds.*` keys and those are
> the keys health scoring reads, so a run's own bar may be a bar its own proposal moved.

これは **EXP-010 で塞いだ穴そのもの**である。フラグでそれを開け直すのは元より悪い。
**最初のガードは不完全だった（同セッション内で自分で見つけて直した）。**
`apply_proposals_path` の有無で判定したが、`--set thresholds.co2_storage_high_kg=99.0` は
同じ4キーを書き換えたうえで **`apply_proposals_path` を残さない**。実際に走らせて確認した:
閾値 99 kg（＝警報帯に一度も入らない）の run が、記録上は「提案なし」に見えた。

そこで **run 実行時に `thresholds_modified` を記録する**ことにした。
scenario.yaml の既定と実効値を実行時点で比べるので、`--set` も `--override-file` も
`--apply-proposals` も一様に捕まる。**後から今の scenario.yaml と比べるのでは駄目**で、
それだと世代が変わるたびに過去の run が丸ごと不合格になる（v4 の O₂ 閾値は 6.0、v5 は 104.25）。

```
thresholds_modified = true   → --yardstick run を拒否
thresholds_modified = false  → 許可
キーが無い（v3〜v5）         → 許可するが「unverified」と明示して出す
```

最後の1つは妥協である。過去 run は自分の閾値が動かされたかを言えない。
**拒否すれば公表値が再現できなくなり、黙って通せば無かった検査をあったことにする。**
出力に `(predates thresholds_modified -- unverified)` と出す。

さらに**どちらの物差しを使ったかを毎回出力し、JSON にも入れる**。
沈黙していたことが EXP-014 の取り違えを生んだので、数字を物差し抜きで読めなくする。

テスト6件で固定（`tests/tools/test_cli_score.py`）:
物差しを名乗ること／二つの物差しが実際に違う総点を出すこと／正規の run は verified で通ること／
**`--set` で閾値を動かした run は拒否すること**／記録前の世代は unverified と出ること／
`--yardstick run` は `--habitat-volume-m3` を取らないこと。

### 検算 — 3世代すべての公表値を再現した

```
             共通3軸(90)   ルール腕   no-op    LLM 平均
v3 (EXP-013)              82.199    68.666   64.068 (n=23)
v4 (EXP-014)              82.199    68.666   61.487 (n=24)
v5 (EXP-015)              82.230    68.666   66.257 (n=24, SD 9.25)
```

検定も一致する（v5: 対ルール腕 −15.973 p<0.000001 / 対 no-op −2.409 p=0.2146）。
**決定的な腕は n=1 なので Welch ではなく1標本 t 検定である**（これも記録に無かった）。

## 2. 共通3軸の変動は、ほぼ全部が「乗員が何人死んだか」

v5 の LLM 24本を軸ごとに分解した（物差しは `run 自身の閾値`）。

```
軸           満点      SD    SD/満点   異なる値の数
残存          50   8.823    17.6%      3      ← 乗員 3 が22本、1 が1本、0 が1本
A 環境        20   0.305     1.5%     22
B 余裕        20   0.033     0.2%      3      ← 実質的に動かない
C 判断         5   1.093    21.9%     24      ← 24本すべて違う値
D 応答         5   1.456    29.1%     20
共通3軸       90   9.052    10.1%     22
```

**共通3軸（90点）の SD 9.05 のうち、残存の SD が 8.82 を占める。**
そして残存は3段階しか取らない。**合計点は「たまたま何人死んだか」をほぼそのまま出している。**

**判断の分解能は C と D にしか無い。**

## 3. C・D を外したのは誤りではなかった。しかし R6 には当てはまらない

EXP-013 が理由を書いている:

> 全 run が持つ3軸（残存50 + A20 + B20 = 90点満点）で比較する。**C・D は actor 操作のある run にしか無い。**

no-op 腕は指令を出さないので C・D が定義できない（実測でも `applicable: false`）。
**no-op を比較対象に含める限り、この判断は正しい。**

**しかし R6 は指令を出す腕どうしの比較である**（ルール腕 vs ハイブリッド腕 vs LLM 腕）。
そこでは C・D が全腕で定義でき、外す理由が無い。

## 4. D 応答は v4 で初めて生きた軸になった。2世代のあいだ測られなかった

D は「**プラントがその step に実際に出せる量を頼んだか**」を見ている
（`delivered_all_it_could / commands`、不足は `shortfalls` に理由つきで載る）。

```
v3   LLM 23本すべて D = 5.000（SD 0）   ← STATE.md の「D 軸は動かない・常に満点」は v3 では正しかった
v4   LLM 24本 D = 2.686 ± 1.17
v5   LLM 24本 D = 2.470 ± 1.49        ← 対ルール腕 −2.530  p<0.000001
```

**定格の不変条件（v4）が D を生きた軸に変えた。** それ以前は per-step の上限が無く、
頼んだものは何でも通ったので全 run が満点だった。上限が入って初めて
「出せない量を頼んだ」が観測可能になった。

**その世代で C・D は報告に入っていなかったので、誰も気づかなかった。**
これが「合計点しか見ない」ことの実害である。

### 既知の穴 — WRS の過大要求は D に映らない

`ref_labeled_rule_base` は D = 5.000 だが、C の内訳を見ると
**WRS を30回・OGS を14回、定格超で要求している**（`oversized_by_kind`）。
D が満点なのは、WRS が `limited_by` を返さないため不足として数えられないからである
（STATE.md の既知課題）。**D はルール腕を実力より良く見せている。**

R6 でこの穴を踏まないこと。**D を単独の結論に使わない。**

## 5. 決定 — 案う（合計を残し、C・D を必ず並記する）

```
案あ  C・D を合計に足して100点にする       → 過去3世代と比較できなくなる
案い  合計をやめて軸別だけにする           → EXP-013〜015 の結論を並べ直せない
案う  合計を残し、C・D を必ず並記する       ← **採用**
```

## 結論

1. **R6 の物差しは既にある。** C・D を報告に入れるだけでよく、新しい指標を発明しなくてよい
2. **公表値は道具に固定した。** 3世代すべての見出し数字を `compare.py` で再現できる
3. **D は単独では使えない**（WRS の穴）。C と併せて読む

## 1. D 軸は信号ではなかった（REFUTED）

`_SATURATION_REASONS`（`scorecard.py`）に `rated_step_capacity` が入っていなかった。
`model.py` は**同じ物理制限を2つの名前で呼ぶ**:

```python
"rated_step_capacity" if spent > tol else "ogs_capacity"
```

片方だけが許可リストにあったので、**同じ物理が指令の順序次第で2通りに採点されていた。**

```
          訂正前                      1語足した後
v3   5.000 SD 0.000 (1通り)     →   5.000 SD 0.000
v4   2.686 SD 1.142 (21通り)    →   5.000 SD 0.000
v5   2.470 SD 1.488 (20通り)    →   5.000 SD 0.000
```

**D の分散は 100% がこの取りこぼし。** 修正済み（`973d2bb`）。
STATE.md の旧記述「D 軸は動かない・プラントが失敗しないので常に満点」が**正しかった**。
私が「訂正」したほうが誤りだった。

## 2. C 軸は判断の質を測っている証拠が無い（REFUTED）

「指令数と無相関（r = −0.040）」は**分母を間違えていた**。`commands_sized`（サイズ判定できた数）
ではなく実際の発行指令数で取ると:

```
v3  r = −0.671        v4  r = +0.205        v5  r = −0.629
```

符号すら世代で安定しない。機構はコードに露出している —
C の `invalid_ops` は `1 − 拒否数/発行数` で、**判断ではなくスキーマ適合度**である。

**決定的な反例**: 共通3軸が no-op と小数点3桁まで一致する3本（軌道が同一）に、C が差をつける。

```
              共通3軸    C       発行指令数
llm_r10       68.666    0.000       76
llm_r4        68.666    2.281       72
llm_r5        68.666    2.723       55
ref_none      68.666     —           0
```

**ばらつきがあることは、何かを測っていることではない。**

さらに `compare.py` の不具合: C は測れなかった部分を除いて満点を縮める（`max_effective`）ため、
**満点が 5 の run と 3 の run が同じ列で平均されていた**（v3 で2本、v4 で2本、v5 で1本）。

## 3. 統計の瑕疵（OVERSTATED）

- 最小検出差は **z 近似**で計算していたのに「1標本 t」と書いた。厳密な t だと
  5.522 / 0.667 / 0.910 で、公表値は一律 4.5% 楽観的
- 軸別 SD の表は母SD、共通3軸の「SD 9.25」は標本SD。**節ごとに推定量が入れ替わっていた**
- D の「n=24」は誤り。1本欠測で n=23
- 「82.230 は `score_run(dir, habitat=None)` が返す」は誤り。返すのは 91.5461 で、
  82.230 は共通3軸の小計。`ea scorecard` が std で出すのも 84.35 ではなく 93.7

## 4. ガードの守備範囲が狭すぎた

`thresholds` は採点バーの一部でしかなかった。監査が**閾値に一切触れず**に:

```
正直な run                        29.4 / 90   乗員 0/4
plant_sim.survival.bands を緩める  78.1 / 90   乗員 4/4
plant_sim.survival.enabled=false   72.6 / 90   乗員 4/4
```

50点（生存）を決めているのは `survival_bands` だった。
**代理指標を1つ選んで経路の全体だと仮定する**という、`apply_proposals_path` のときと
同じ誤りを繰り返していた。`scoring_bar_modified` に置き換えて修正済み（`d42d8a5`）。
`--baseline` と `compare.py` にも同じガードを入れた。

**ただし設計提案（LLM）からは `survival.bands` に手が届かない**
（`ALLOWED_SET_PARAMETER_TARGETS` に無い）。届くのは `--set` と `ea job`＝実験者の手。
**EXP-010 が想定した脅威そのものは、この間も塞がっていた。**
