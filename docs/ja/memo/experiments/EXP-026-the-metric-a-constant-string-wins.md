## 何を監査にかけたか

EXP-025 第2版 — 「designer の判断点を1つずつ LLM に渡す梯子」。
第1版（競争の設計）はユーザーの指摘で既に撤回済みで、**第2版はその反動で書かれた**。

**3体とも独立に「この設計のままでは測ってはいけない」を返した。**

# 第1部 — 主指標が壊れていた

## ★ 救出率は、run を一切読まない定数文字列で 10/10 になる

集合A の10本の提案を、**次の1行に差し替えて**評価した:

```json
{"change_kind":"set_parameter","payload":{"target":"thresholds.co2_storage_high_kg","value":1.8}}
```

```
判断ゼロの定数文字列による救出: 10/10
```

**主指標は「良い提案か」ではなく「ある1つの欄に 1.8 以下の数を書いたか」を測っていた。**
監査はさらに `value=true`（真偽値）・`value=-5.0`（負の CO₂ 警報線）・`value=0.0` でも
救出 +1 になることを実測している。**型エラーと物理的に無意味な負値が満点を取る。**

## ★ 副指標「棄却率」は、中身を見ない検証器の上に載っていた

```
graph_rewire {"a":1}                     → 通る（payload の中身を一切見ない）
service_config {"service":"request_co2"} → 通る（amount が無く、何も書き込まない）
```

そして `graph_rewire` は **ros2 バックエンドでしか読まれない**（`scenario_run.py:172`）。
本件は全て plant_sim なので**構造的に 100% 無効**である。

**probe の「通った3件」を実際に適用したところ、plant_sim が読む値の変化は 0件だった。**

> **probe の真の「何も起きなかった率」は 79% ではなく 14/14 = 100% である。**

**⇒ P1（棄却率を 20% 未満に下げる）は、モデルが `graph_rewire` にゴミを1件出すだけで達成できる。**
そして解釈規則は P1・P2 が当たれば「AI は行動空間を教えれば使える」と読ませる。
**実質ゼロの変化から、著者が望む結論が出る経路が実在した。**

# 第2部 — さらに重い3つ

## ★ LLM が JSON を吐き損ねると、ルールの正解が黙って代筆される

`ssos_post_run_design.py:182-197`。`agent.deliberate()` が `None` を返すと
`build_design_proposals_from_run(decision_source="llm_parse_fail")` にフォールバックする。
**その提案はルールのものと同一で、集合A で 10/10 救出する。**

```
記録される姿   parse_notes=[]（棄却ゼロ）／thresholds.* を提案／乗員 +1
＝ 著者が「いちばん重い結果」と呼んだ形が、**LLM の完全な失敗から生成される**
```

空応答の経路は塞がっていない（`vllm.py:275-287` はあらゆる例外で `return ""`、
同 269-273 に「think が completion budget を食い尽くして content が空」の既知警告。
probe の設定は `think: true, max_tokens: 16384`）。

**そして腕2 のプロンプトは腕1 より長い。長くする編集そのものが、
パース失敗率 → ルール代筆率 → 救出率を押し上げる。** 著者の望む方向と一致した交絡である。
**判定規則に `decision_source == "llm_parse_fail"` の除外が1行も無かった。**

## ★ designer は「乗員」の存在を知らされていない

主指標は「乗員救出」である。プロンプト構築コード（`build_llm_post_run_situation`）を検索した:

```
crew / 乗員 / remaining / lost / survival / occupant  → **1語も出てこない**
summary.json にはある: crew_initial 4, crew_remaining, crew_lost, crew_lost_by_cause
```

**集合A の10本は乗員が1人死んだ run だが、モデルはそれを知らされないまま
「救えなかったね」と採点される。**

**腕2 は「行動空間が分からない」と「目的が分からない」を分離できない。**
probe は乗員 4/4・health "safe" だったので、この穴は probe では見えなかった。

## ★ 渡す予定だった10件のうち、6件は構造的に死んでいる

`policy.py` の `merge_labeled_policy_from_thresholds` が、`apply_design_proposals` の**後**に
`agents.actor.policy.*` を `thresholds.*` で無条件に上書きする（`scenario_run.py:480`）。
actor が `labeled_rule_base` である限り必ず発火し、本実験は全てそれである。

```
thresholds.co2_storage_high_kg      → 救出 +1        ← 唯一の正解
thresholds.o2_storage_low_kg        → 乗員は動かず、水だけ悪化
thresholds.co2_storage_critical_kg  → no_effect
thresholds.product_water_low_l      → no_effect
agents.*.policy.* ×6                → **全て no-op（上書きされる）**
```

**「行動空間を渡す」の中身は、10枚のドアのうち6枚が溶接済み・2枚が空室・1枚が正解のリストである。**
**「答えは教えない」と書いたが、思っていたより答えに近い。**

```
 service_config を無効と測定」   残り114/56 は thresholds と束ねられていた。**外挿を測定として引いていた**
```

## そして、梯子を降りる枝が1つも無かった

```
P1○P2○P3○ → 腕3 へ進む     P1○P2○P3× → 前進（著者の望み）
P1×       → 診断（方向は否定されない）   P4× → 撤回自体を見直す
P1○P2× / P1×P2○ → **規則が存在しない**
```

**「合成しても効かないので、この道を降りる」という出力を持つ枝が無い。**
第1版にあった集合B（ルールが何も見つけられなかった run の全部＝否定的に終われる唯一の場所）を、
**第2版で落としていた。** 撤回の反動で、終端が「続く」側にだけ寄っていた。

## 加えて、腕3 も既に退化している（実測）


# 結論

**4.5時間の測定を実行しない。** EXP-025 第2版を撤回する。
**GPU は probe 1本（4分27秒）のみ使用。**

## 測る前に直すもの（すべて GPU 0秒）

```
計装  生応答を全文保存（現在 head240+tail240 で probe は 9080字消失）
      棄却された change を {change_kind, payload, reason} で保存（現在は理由なし1行）
      change_count == 0 でもファイルを書く（現在は標本から消える）
      decision_source == "llm_parse_fail" を全指標から除外し、発生率を第一級の結果にする
指標  主指標を「有効提案率」＝ 9指標のうち1つでも動かした提案の割合 に変える
      probe に当てると 0/14 になることを先に記録する
      救出は二値でなく「救出する最大の閾値」にする（1.8 と 0.2 が同点なのを解消）
入力  designer に乗員（crew_initial / remaining / lost / lost_by_cause）を渡す
      → これは「目的を伝える」ことであって「答えを教える」ことではない
検証  set_parameter.value に数値・有限の検査を入れる（他2種は既にある）
設計  対象を集合A から A∪B に（ルールの真の救出能力は 10/10 ではなく 10/20）
      プラセボ腕（同量・同形式で許可外キーを列挙）を足す
      降りる条件を数字で事前登録する
      腕1.5（スキーマのみ）を足すか、棄却を理由別に割る
手順  プロンプトを測定前にコミットし、diff と生成コードを EXP に貼る
      一覧は sorted() で固定（frozenset のまま join すると**プロセスごとに順序が変わる**）
      段階1（1シナリオ×5回×3腕＝67分）のゲートを先に置く
```
