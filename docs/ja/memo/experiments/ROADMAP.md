# 進め方 — 何を、どの順で、なぜその順で

2026-08-28。**[STATE.md](STATE.md) が現在地、この文書が道順。**

出口は**動く仕組み**であり、質が伴えば本家として貢献する。したがって成果物は
シミュレータの現実性ではなく、**エンジニアリングの意思決定を検証可能にする層**である。

## 原則1 — 誤りは直す。簡略化は放置してよい

底なし沼に落ちないための基準。

| | 例 | 判定 |
|---|---|---|
| **誤り** | O₂ 8 kg（388 m³ のキャビンでは窒息水準。物理的にありえない） | **直す** |
| **簡略化** | 故障が二値・決め打ち（粗いが嘘ではない） | 目的が要求するまで放置 |
| **簡略化** | N₂ を持たない（ppO₂ だけで近似） | 診断経路が要るまで放置 |

見分け方は「**それが原因で、仕組みが自信を持って間違った判定を出すか**」。
O₂ 8 kg は EXP-014 の全滅4本を「O₂ 死」と判定させた。正しい物理では起きない死に方である。

## 原則2 — 変更の種類でコストが桁違い。順序はそれで決まる

実測（2026-08-28）:

```
ルール腕 1 run   0秒       ← 決定的
LLM 腕   1 run   520秒     ← 24本で 3.5時間
再採点            無料       ← telemetry から後付けで計算できる（v3/v4 で実証済み）
```

| 変更の種類 | 手戻り | 検証手段 |
|---|---|---|
| **採点・基準値を変える** | **ゼロ** | 既存 run を再採点するだけ |
| **物理を変える** | 全 run が比較不能 | 決定的な腕（0秒）＋ 物理ゲート ＋ テスト |
| **観測・プロンプトを変える** | LLM run のみ無効 | 同上（ただし LLM の再測定が要る） |

**したがって「無料 → 物理 → 観測」の順に進め、LLM の測定は問いが新しくなったときだけ払う。**

## 原則3 — ②を飛ばさない

各増分の手順:

```
① 設計文書を書く   選択肢と帰結を数字つきで。判断は人間に委ねる
② 判断する         ← ここを飛ばさない
③ 実装             決定的な腕とテストで即検証（秒単位）
④ 記録してコミット  なぜその選択をしたかを本文に残す
```

WRS の定格（2026-08-28）は①〜④を踏んで実装1回で済んだ。
levers の非対称は②を経ずに走らせ、**LLM run 7本を捨てた**。

# 道順

## 進捗の物差し — 規格に紐づいた軸を1本ずつ増やす

「どこまでリアルにするか」は際限がないが、「この軸は公表規格に照らせるか」には答えがある。
**規格が終点を決めてくれるので沼にならない。**

`reference_limits.py` が現状を自己申告している:

```
CO₂   ✅ NASA-STD-3001 [V2 6004] / OCHMO-TB-004（3帯）
O₂    ❌ [V2 6003] — 数値が未出典、かつ**モデルが間違っている**（在庫であって大気でない）
水    ❌ [V2 6109] — **数値が未出典なだけ。モデルは正しい**
総圧  ❌ [V2 6006] — 未着手
```

**いま 1/3。** O₂ と水では欠けているものの性質が違い、それが順序を決める。

## R1 — 水の基準値を出典から取る ✅ 完了（2026-08-28）

```
出典   OCHMO-TB-027 Water -- Human, Rev C, 11/29/2023
       https://www.nasa.gov/wp-content/uploads/2023/12/ochmo-tb-027-water.pdf
要求   NASA-STD-3001 Volume 2 [V2 6109] Water Quantity
値     Potable Water for Hydration: Minimum 2.5 L (84.5 fl oz) per crewmember per day
```

**表の他の2行はスカラーにならないので採らなかった** — 個人衛生は "Mission dependent"、
洗眼は「乗員あたり 500 mL」で日次レートではない。

### 2.28 と 2.5 は矛盾しない（確認済み）

一見 plant_sim の `potable_water_kg_day_person: 2.28` が規格の最低 2.5 を下回るように見えるが、
**別の量である。**

```python
# config.py の不変条件
req(urine 1.50 + condensate 0.75 + unrecoverable 0.03 == potable 2.28,
    "crew water outputs must equal potable intake")
```

2.28 は**乗員を通過する量**で、水収支が閉じるよう固定されている。2.5 は
**システムが供給できねばならない量**。2.5 ≥ 2.28 は要求として自然である。

### 採点の形 — 「乗員何日ぶんか」

[V2 6109] は**供給レート**であって在庫の下限ではない。標準は
"for the expected needs of each mission" としか言わず**保有期間を定めていない**ので、
こちらで床を発明せず、在庫を規格の配給率で割って**乗員日**に換算するに留めた。

```
min_crew_days = product_water_reserve_l / (2.5 L/crew-day x crew)
```

**plant_sim 自身の 2.28 で割らない。** それは run を自分自身で採点することになる。

### 手戻りゼロの実証

既存 run を**1本も再実行せず**、再採点だけで新しい軸が入った:

```
v3 ルール  最小 7.90 乗員日    v4 ルール  最小 7.89 乗員日
v4 no-op   最小 7.49 乗員日    v4 llm_r4  最小 7.74 乗員日
```

**世代を跨いで採点し直せる**（telemetry を捨てていないため）。

```
規格に紐づいた軸:  CO₂ ✅  水 ✅  O₂ ❌  → 2/3
`ea score` の "not scored against a standard" は o2 のみになった
```

## R2 — 酸素をキャビン大気にする（物理・失敗モードは足さない）

**誤りの訂正。リークは含めない。**

- 2プール模型（供給タンク ↔ キャビン大気）
- **キャビンを「気体の質量の集まり」として扱う構造を保つ。**
  `cabin_co2_kg` と同じ形で `cabin_o2_kg` を置く。ppO₂ をスカラーとして直接持たない
- **失敗モードは追加しない**

> **訂正（2026-08-28）** — 当初ここに「不活性ガス（N₂）のプールを今のうちに持たせる。
> 無いとリークに圧力の署名が作れず、後から模型の再設計になる」と書いた。**過剰だった。**
>
> 分圧は理想気体の法則から**その気体の質量と容積だけ**で出る。他に何が入っているかは
> 関与しない（`co2_kg_for_ppco2` が既にそう書かれている）。したがって
> `cabin_o2_kg` だけで ppO₂ は計算でき、[V2 6003] に照らせる。
> そして後から `cabin_n2_kg` を足すのもフィールド1つで、**再設計にはならない。**
>
> N₂ が要るのは総圧 [V2 6006] を載せるときと、R4 でリークの診断
> （「ppO₂ も総圧も下がる＝リーク」）を作るときだけ。**R2 には要らない。**
> 「それを要求する測定が存在してから入れる」という原則を、自分で破りかけていた。

修正後の姿（算術）:

```
キャビン O₂ 108 kg / 乗員4の消費 3.36 kg/day → 32日ぶんの余裕
観測窓 16.7時間では ppO2 が 3.4 mmHg しか動かない  → **酸素は「正しいが動かない軸」になる**
水も動かない（no-op 腕でも min 74.9 L / 帯 50 L を一度も割らない）
→ シナリオは **CO₂ 管理の試験**になる
```

**これは弱体化ではなく明確化。** EXP-014 の全滅4本は 8 kg という誤設定が生んだ人工的な死で、
それが消えて規格に紐づいた唯一の動く軸だけが残る。

| | |
|---|---|
| 判断が要るもの | ①供給とキャビンの境界（OGS はキャビンに直接吐くか、タンク経由か）<br>②[V2 6003] の数値レンジを一次資料から読む（R1 と同じ作業） |
| 完成の定義 | `not scored against a standard: o2` が消える／物理ゲート通過／テスト差分ゼロ／ルール腕が生存 |
| 検証 | 決定的な腕（0秒）＋ ゲート ＋ テスト。**LLM は走らせない** |
| 手戻り | 全 run が比較不能。ただし**新しい問いが生まれないので LLM の測り直しは不要** |

## R3 — 採点式に根拠を与える（無料・物理を触らない）

A〜D の配点だけ「この枝の独断」になっている。

telemetry から再採点できるので**いつやっても無料**。R2 の後に置くのは、
軸が 2/3 まで揃ってからのほうが配分を議論しやすいため。

| | |
|---|---|
| 判断が要るもの | A〜D の重み。**本来チームが決めるべきもの** |
| 完成の定義 | 各軸の配点に、規格または明示した設計判断の根拠がある |

## R4 — リーク ＋ 対処手段（新しい問いが生まれる）

**ここで初めて「診断できるか」を測る。** 前段までは持続性しか測れていない。

リークだけを入れてはいけない。**対処手段とセットでなければ実験にならない**（計算済み）:

```
OGS の補填余力 5.89 kg-O2/day → 支えられるリーク上限は直径 1.58 mm

  直径 1.0 mm   漏れ  10.1 kg/day   ✅ OGS を回し続ければ支えられる
  直径 1.6 mm   漏れ  25.8 kg/day   境界
  直径 4.1 mm   漏れ 169.2 kg/day   ❌ 33.5 kg-O2/day 不足。供給では絶対に届かない
```

**16.7時間で警報域に落とせる 4.1 mm は、供給では手も足も出ない。**
補修手段が無ければエージェントが何をしても結末は同じで、判断を測る実験にならない。

測りたいのは「もっともらしい誤り」である:

```
リーク発生（明示フラグは出さない）
  ↓ 観測できるのは ppO2 と総圧の低下だけ
  「OGS を回す」       → 一時的に持ち直すが下げ止まらない（酸素を作って穴から捨てる）
  「seal_leak を打つ」 → 止まる（正解）
```

診断は物理から出る:

```
ppO2 も総圧も下がる → リーク（圧力に比例＝指数減衰）
ppO2 だけ下がる     → 消費または供給停止（一定レート）
```

| | |
|---|---|
| 判断が要るもの | ①対処手段（補修コマンド／区画隔離／供給で耐える）<br>②補修に代償を与えるか<br>③リークの規模と時刻、明示するか<br>④総圧をモデル化するか（**N₂ をここで足す**。診断経路を作るなら要る） |
| 完成の定義 | D軸が満点で張り付かなくなる／ルール腕が診断して生存できる |
| 手戻り | 物理変更。**ここで初めて LLM の測定を払う価値が出る** |

## R5 — 一度だけ測る（v5）

**3.5時間を払うのはここ1回。** R1〜R4 を通して LLM を走らせないので、
設計判断を間違えても失うのは秒である。

- 予測を**測定前にコミット**する（手順ルール5）
- 直前に `backup.sh`
- 新しい問い: **診断能力に差が出るか**（持続性は v4 で測り終えている）

# 順序の要約と、その理由

```
R1  水の基準値      無料      1/3 → 2/3
R2  酸素の物理      物理変更   誤りの訂正。リークは入れない。ただし**リーク可能な形**にする
R3  採点式の根拠    無料      本家に出すための弱点補強
R4  リーク＋対処    物理変更   新しい問い（診断）が生まれる
R5  測定 v5        3.5時間   ここ1回だけ
```

**無料のものを先に、高いものを後に、測定は最後に1回。**
