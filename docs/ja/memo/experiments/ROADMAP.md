# 進め方 — 何を、どの順で、なぜその順で

2026-08-28。**[STATE.md](STATE.md) が現在地、この文書が道順。**

出口は**動く仕組み**であり、質が伴えば本家として貢献する。したがって成果物は
シミュレータの現実性ではなく、**エンジニアリングの意思決定を検証可能にする層**である。

## 原則1 — 誤りは直す。簡略化は放置してよい

底なし沼に落ちないための基準。

| | 例 | 判定 |
|---|---|---|
| **誤り** | O₂ 8 kg（388 m³ のキャビンでは窒息水準。物理的にありえない） | **直す** |
| **簡略化** | 故障が二値・決め打ち（粗いが嘘ではない） | 目的が要求するまで放置 |
| **簡略化** | N₂ を持たない（ppO₂ だけで近似） | 診断経路が要るまで放置 |

見分け方は「**それが原因で、仕組みが自信を持って間違った判定を出すか**」。
O₂ 8 kg は EXP-014 の全滅4本を「O₂ 死」と判定させた。正しい物理では起きない死に方である。

## 原則2 — 変更の種類でコストが桁違い。順序はそれで決まる

実測（2026-08-28）:

```
ルール腕 1 run   0秒       ← 決定的
LLM 腕   1 run   520秒     ← 24本で 3.5時間
再採点            無料       ← telemetry から後付けで計算できる（v3/v4 で実証済み）
```

| 変更の種類 | 手戻り | 検証手段 |
|---|---|---|
| **採点・基準値を変える** | **ゼロ** | 既存 run を再採点するだけ |
| **物理を変える** | 全 run が比較不能 | 決定的な腕（0秒）＋ 物理ゲート ＋ テスト |
| **観測・プロンプトを変える** | LLM run のみ無効 | 同上（ただし LLM の再測定が要る） |

**したがって「無料 → 物理 → 観測」の順に進め、LLM の測定は問いが新しくなったときだけ払う。**

## 原則3 — ②を飛ばさない

各増分の手順:

```
① 設計文書を書く   選択肢と帰結を数字つきで。判断は人間に委ねる
② 判断する         ← ここを飛ばさない
③ 実装             決定的な腕とテストで即検証（秒単位）
④ 記録してコミット  なぜその選択をしたかを本文に残す
```

WRS の定格（2026-08-28）は①〜④を踏んで実装1回で済んだ。
levers の非対称は②を経ずに走らせ、**LLM run 7本を捨てた**。

## 原則4 — 高い測定の前に、独立監査を通す（2026-08-28 追加）

```
高い測定（GPU 3.5時間・LLM は seed を固定しても再現しない）を払う前に、
独立監査を走らせ、**その決定的な指摘を自分で再現する**まで着手しない。
```

**発動条件**（どれか1つで十分）:

- 測定が高価または不可逆（作り直せないデータ）
- **設計・物差し・予測が同じ手から出ている** ← これが主たる条件。能力の話ではなく構造の話
- 他人が土台にする結論や記録を出そうとしている
- 自分が導入・修正したばかりの計器で判断しようとしている

**やり方**: 観点の違う監査を**並列で**走らせ、互いの結論を知らせない
（①主張を生データから再導出、②計器とガードを敵対的に破る、③事前登録として査読）。
どの指示にも「**著者は自分を騙していると仮定せよ。文書・コメント・コミットメッセージを信用するな**」を入れる。

**そして指摘を鵜呑みにしない。** 判断を変える指摘は自分のコマンドで再現し、自分の数字で報告する。
再現しなかったものは「再現しなかった」と書く。

**実績（2026-08-28、費用はトークンのみ・GPU 0秒）**: 承認1つ手前だった 3.5時間の測定について、
主指標の分散が100%採点の取りこぼしだったこと、第2の指標が軌跡の同一な run を分離していたこと、
操作するはずの変数が設定2つ・モデル無しで天井に届くこと、採点式が「少なく頼む」を満点にしていたこと、
1時間前に入れたガードが1フィールド隣で破れること（乗員 0/4 → 4/4）を検出した。

**共通する形は「本物の代わりに代理指標を選び、その代理を全体だと仮定する」。**
設計の内側からは非常に見えにくい。

**危険信号**: 「A は B に勝つ」を測る前に書いている／主指標が自分でこの作業中に入れた軸／
**ばらつきを分解能と読んでいる**（分散は妥当性ではない。**同一のものを分離していないか**を示せ）／
無料の基準線と、配線だけ揃えたプラセボが無い／害に名前が無い（分母に「悪い側」が入っているか）。

（セッション側の仕組み: `~/.claude/skills/pre-measurement-audit`）

## R1 — 水の基準値を出典から取る ✅ 完了（2026-08-28）

```
出典   OCHMO-TB-027 Water -- Human, Rev C, 11/29/2023
       https://www.nasa.gov/wp-content/uploads/2023/12/ochmo-tb-027-water.pdf
要求   NASA-STD-3001 Volume 2 [V2 6109] Water Quantity
値     Potable Water for Hydration: Minimum 2.5 L (84.5 fl oz) per crewmember per day
```

**表の他の2行はスカラーにならないので採らなかった** — 個人衛生は "Mission dependent"、
洗眼は「乗員あたり 500 mL」で日次レートではない。

### 2.28 と 2.5 は矛盾しない（確認済み）

一見 plant_sim の `potable_water_kg_day_person: 2.28` が規格の最低 2.5 を下回るように見えるが、
**別の量である。**

```python
# config.py の不変条件
req(urine 1.50 + condensate 0.75 + unrecoverable 0.03 == potable 2.28,
    "crew water outputs must equal potable intake")
```

2.28 は**乗員を通過する量**で、水収支が閉じるよう固定されている。2.5 は
**システムが供給できねばならない量**。2.5 ≥ 2.28 は要求として自然である。

### 採点の形 — 「乗員何日ぶんか」

[V2 6109] は**供給レート**であって在庫の下限ではない。標準は
"for the expected needs of each mission" としか言わず**保有期間を定めていない**ので、
こちらで床を発明せず、在庫を規格の配給率で割って**乗員日**に換算するに留めた。

```
min_crew_days = product_water_reserve_l / (2.5 L/crew-day x crew)
```

**plant_sim 自身の 2.28 で割らない。** それは run を自分自身で採点することになる。

### 手戻りゼロの実証

既存 run を**1本も再実行せず**、再採点だけで新しい軸が入った:

```
v3 ルール  最小 7.90 乗員日    v4 ルール  最小 7.89 乗員日
v4 no-op   最小 7.49 乗員日    v4 llm_r4  最小 7.74 乗員日
```

**世代を跨いで採点し直せる**（telemetry を捨てていないため）。

```
規格に紐づいた軸:  CO₂ ✅  水 ✅  O₂ ❌  → 2/3
`ea score` の "not scored against a standard" は o2 のみになった
```

```
規格に紐づいた軸  2/3 → **3/3**（CO₂・水・O₂）
"not scored against a standard"  → 0行
決定的な腕  no-op は正常酸素帯を 36/50 step 割る／ルール腕は 14/50（連続1）
```

## R2 の設計（記録）

**設計文書: [o2_cabin_atmosphere_design.md](../ssos_eclss_loop/o2_cabin_atmosphere_design.md)（2026-08-28、判断待ち）**

一次資料から Table 6.2-1 を読んだ結果、**[V2 6003] は ppO₂ ではなく PIO2（吸入酸素分圧）で
規定されていた**（`PIO2 = (PB - 47) x FIO2`）。[V2 6004] の CO₂ が乾燥分圧なのと扱いが違う。
総圧一定を仮定すれば `ppO2 = PIO2 x 1.0659` で換算でき、**R2 では成立する**（リークが無いため）。

**判断点は2つではなく3つになった。** 数字を出したことで、
「帯を割ったときに乗員を失わせるか」が新たに要ることが分かった
（キャビン大気にすると `o2_storage_low_kg: 6.0` が無意味になるため）。

**誤りの訂正。リークは含めない。**

- 2プール模型（供給タンク ↔ キャビン大気）
- **キャビンを「気体の質量の集まり」として扱う構造を保つ。**
  `cabin_co2_kg` と同じ形で `cabin_o2_kg` を置く。ppO₂ をスカラーとして直接持たない
- **失敗モードは追加しない**

> **訂正（2026-08-28）** — 当初ここに「不活性ガス（N₂）のプールを今のうちに持たせる。
> 無いとリークに圧力の署名が作れず、後から模型の再設計になる」と書いた。**過剰だった。**
>
> 分圧は理想気体の法則から**その気体の質量と容積だけ**で出る。他に何が入っているかは
> 関与しない（`co2_kg_for_ppco2` が既にそう書かれている）。したがって
> `cabin_o2_kg` だけで ppO₂ は計算でき、[V2 6003] に照らせる。
> そして後から `cabin_n2_kg` を足すのもフィールド1つで、**再設計にはならない。**
>
> N₂ が要るのは総圧 [V2 6006] を載せるときと、R4 でリークの診断
> （「ppO₂ も総圧も下がる＝リーク」）を作るときだけ。**R2 には要らない。**
> 「それを要求する測定が存在してから入れる」という原則を、自分で破りかけていた。

修正後の姿（算術）:

```
キャビン O₂ 108 kg / 乗員4の消費 3.36 kg/day → 32日ぶんの余裕
観測窓 16.7時間では ppO2 が 3.4 mmHg しか動かない  → **酸素は「正しいが動かない軸」になる**
水も動かない（no-op 腕でも min 74.9 L / 帯 50 L を一度も割らない）
→ シナリオは **CO₂ 管理の試験**になる
```

**これは弱体化ではなく明確化。** EXP-014 の全滅4本は 8 kg という誤設定が生んだ人工的な死で、
それが消えて規格に紐づいた唯一の動く軸だけが残る。

| | |
|---|---|
| 判断が要るもの | ①供給とキャビンの境界（OGS はキャビンに直接吐くか、タンク経由か）<br>②[V2 6003] の数値レンジを一次資料から読む（R1 と同じ作業） |
| 完成の定義 | `not scored against a standard: o2` が消える／物理ゲート通過／テスト差分ゼロ／ルール腕が生存 |
| 検証 | 決定的な腕（0秒）＋ ゲート ＋ テスト。**LLM は走らせない** |
| 手戻り | 全 run が比較不能。ただし**新しい問いが生まれないので LLM の測り直しは不要** |

## R3 — 採点式に根拠を与える（調査済み・判断待ち）

**[R3-scorecard-weights.md](R3-scorecard-weights.md) に調査結果と選択肢。**

ただし根拠にできる測定はある。「何もしなければどれだけ速く殺すか」の実測（乗員4・400 step）:

```
        警報帯        致死帯
CO2      4.3時間      50.0時間      ← CO2 だけが現実的な時間で殺す
O2       4.7時間      133時間でも未到達
水     130.7時間      133時間でも未到達
```

選択肢は4案（到達時間で決める／等配分／合算をやめる／決めない）。
**案1（到達時間）は採るべきでない** — 重みが運用点から出ると、運用点を変えて点数を動かせる。

## R4 の設計（記録・着手時に使う）

**ここで初めて「診断できるか」を測る。** 前段までは持続性しか測れていない。

リークだけを入れてはいけない。**対処手段とセットでなければ実験にならない**（計算済み）:

```
OGS の補填余力 5.89 kg-O2/day → 支えられるリーク上限は直径 1.58 mm

  直径 1.0 mm   漏れ  10.1 kg/day   ✅ OGS を回し続ければ支えられる
  直径 1.6 mm   漏れ  25.8 kg/day   境界
  直径 4.1 mm   漏れ 169.2 kg/day   ❌ 33.5 kg-O2/day 不足。供給では絶対に届かない
```

**16.7時間で警報域に落とせる 4.1 mm は、供給では手も足も出ない。**
補修手段が無ければエージェントが何をしても結末は同じで、判断を測る実験にならない。

測りたいのは「もっともらしい誤り」である:

```
リーク発生（明示フラグは出さない）
  ↓ 観測できるのは ppO2 と総圧の低下だけ
  「OGS を回す」       → 一時的に持ち直すが下げ止まらない（酸素を作って穴から捨てる）
  「seal_leak を打つ」 → 止まる（正解）
```

診断は物理から出る:

```
ppO2 も総圧も下がる → リーク（圧力に比例＝指数減衰）
ppO2 だけ下がる     → 消費または供給停止（一定レート）
```

| | |
|---|---|
| 判断が要るもの | ①対処手段（補修コマンド／区画隔離／供給で耐える）<br>②補修に代償を与えるか<br>③リークの規模と時刻、明示するか<br>④総圧をモデル化するか（**N₂ をここで足す**。診断経路を作るなら要る） |
| 完成の定義 | D軸が満点で張り付かなくなる／ルール腕が診断して生存できる |
| 手戻り | 物理変更。**ここで初めて LLM の測定を払う価値が出る** |

## R6 — ハイブリッド腕（Flow Engineering 型）

**2026-08-28 追加。設計は v5 の結果を待つ（理由は下）。**

### なぜ要るか — いまの比較は「合成」ではなく「競争」になっている

```
現在        LLM 単独  vs  ルール単独  vs  何もしない  ── 三者が同じ仕事を奪い合う
あるべき姿  流れはルールで固定し、判断の点にだけ LLM を置く  ── 合成
```

**この枝のデータ自体が、分離が不適切であることを示している**（EXP-014）:

```
初回 ARS 発行    LLM 中央値 step 13  ／  ルール腕 step 13   ← 完全に一致
ARS を出した step  LLM 中央値  4/50   ／  ルール腕 37/50     ← 9倍
```

**LLM は「気づく」ことはできる。「続ける」ことができない。**
続けることは、そもそも LLM に任せるべき仕事ではない。いまの実験は両方をやらせている。

### 既にループは持っている。全実験でそれを切っている

```
ea run --design-mode llm  →  LLM が設計提案を出す        ← 判断
ea evaluate               →  対照実験で検証、物差しは凍結  ← 決定論
                          →  verdict: improved / refused
```

`design_proposals.py` には `design_domain: "ssos_graph"` と `graph_rewire` があり、
**Systems Graph の芽もある。** しかし:

```
$ grep design-mode ~/ea-runs/analysis-tools/*.sh
  → 7スクリプト全部が --design-mode none
```

**この枝でいちばん Flow Engineering 的な部分を、毎回オフにして測っている。**

### 決定論で固定する / LLM に置く

```
ルールで固定（LLM が苦手なもの）
  ・毎 step の監視ループ
  ・帯を割ったら発火し、回復目標まで続ける      ← 「持続」
  ・定格の不変条件・物理ゲート・規格照合

LLM に置く判断点（候補。**どれを選ぶかは v5 の結果で決める**）
  a. 優先順位   ARS と OGS が同時に必要で行動数に上限があるとき、どちらを先に
  b. 要求量     goal をいくつにするか（※ ARS では現在無効。R3 の宿題）
  c. 診断       症状から原因を推定（※ R4 が要る。将来フェーズ）
  d. 設計提案   run 後の改善提案 ← **実装済み・未使用**
```

### ★ EXP-015 が答えを出した（2026-08-28）

**a（優先順位）は LLM に渡さない。ルールで固定する。**

```
OGS 10回以上の10本  O₂帯割れ 中央  5/50   ← ルール腕(14/50)より良い
OGS 10回未満の14本  O₂帯割れ 中央 36/50   ← no-op と同じ
run ごとの配分: ARS 0/OGS 45 から ARS 37/OGS 1 まで、ばらばら
```

**能力の問題ではなく一貫性の問題である。** LLM は O₂ を管理「できる」が、
する run としない run に割れる。渡せば run ごとに違う配分になる。

**c（診断）は R4 が将来フェーズなので当面測れない。**

**残る候補は b（要求量）と d（設計提案）。**
- b は ARS で無効（定格で頭打ち）だが、**OGS と WRS では「量」なので効く**
- d は**実装済みで一度も測っていない。いちばん Flow Engineering 的**

### 設計を v5 の後に回す理由

**事前登録した P4 が、そのまま核心的な設計判断になる。**

```
P4: LLM は O₂ を CO₂ より優先し、配分を間違える

  当たったら → 優先順位づけは LLM の弱点。**a はルールで固定すべき**
  外れたら   → 優先順位づけは LLM の強み。**a を判断点として渡すべき**
```

**真逆の設計になる。** いま書けばどちらかは確実に捨てることになる。
序盤2本（n=2、結論ではない）は v4 と逆の傾向を見せており、実際に転びうる:

```
v4  OGS 492回 / ARS 426回          ← OGS 優位
v5  llm_r1 ARS 26 / OGS 4、llm_r2 ARS 21 / OGS 3  ← ARS 優位
```

**候補を並べることは v5 に依存しない。選ぶことだけが依存する。**

### 完成の定義

- ハイブリッド腕が、既存の2腕と**同じ物差しで**比較できる（物理変更なし＝手戻りゼロ）
- 判断点を1つずつ変えた腕を並べ、**LLM をどこに置くと効き、どこに置くと害になるか**が測れる

### 先に言っておくこと

**ハイブリッド腕はほぼ確実にルール腕に勝つ**（ルール腕の持続性を持ったうえで、
判断点だけ LLM に置くので）。**それ自体は面白い結果ではない。**

面白いのは「**どこに置くと効き、どこに置くと害になるか**」であり、
測るべきはハイブリッド腕そのものではなく**判断点ごとの寄与**である。
測定の枠組み（対照実験・物差し凍結・規格照合）はそのまま使える。

# 順序の要約と、その理由

```
R1  水の基準値      ✅ 完了       1/3 → 2/3
R2  酸素の物理      ✅ 完了       2/3 → 3/3
R3  採点式の根拠    調査済み・チーム判断待ち（重みは出典から引けないと判明）
                   **R6 の障害ではない** — 主指標は B の CO₂（規格 [V2 6004] 紐づけ）で取れる
                   ※「分解能は C・D にある」は撤回済み（EXP-016 の訂正・独立監査3体）
R4  リーク＋対処    ⏸ 将来フェーズ
R5  測定 v5        ✅ 完了（EXP-015）
R6  ハイブリッド腕  ⏸ 判断点が全て退化（EXP-017）
→ **次は「置く場所を作る」**（EXP-017 の4案）
   案1（指令数の上限）は退化（EXP-018）。案4（修理と診断）も退化（EXP-019）
   **同じ壁に3回。困るものが CO₂ しか無い。→ 次は案3**（GPU はここまで0秒）
```

**R6 は「AI は上手いか」から「AI をどう組み込めば上手くなるか」への転換である。**
前者は3世代測って答えが出た。後者はまだ測っていない。

**R4 を送ったことで物理が確定し、R5 は完了した（EXP-015）。**
そして EXP-017 が、その確定した物理には**代償が無い**ことを示した。
判断を置く場所を作るには、R4 で送った物理変更のどれかを取り戻す必要がある。

**無料のものを先に、高いものを後に、測定は最後に1回。**
