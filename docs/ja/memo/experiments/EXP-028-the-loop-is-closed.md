## 何をしようとしていたか

[EXP-027](EXP-027-the-designer-layer-degenerates-too.md) の規律
「**設計文書を書く前に、任務が定数で解けないかを見る**」に従い、案3
（水のために運用点を締める）の設計文書を書く前に、その前提を確かめた。

案3 の約束は「水を締めれば代償が生まれ、判断を置く場所ができる」。
**前提は「締めたあと、最適な政策が定数でなくなること」**である。それを直接測った。

事前登録（予測・判定規則・撤回条件6件）は測定前にコミットした。**予測は2つとも外れている。**

## 答え — 締めても代償は生まれない。ARS と水はそもそも結合していない

**これが決定打である。乗員を4人に固定して、ARS の活動量だけを変えた:**

```
co2_high   乗員   ARS指令   最小水位L    最終水位L
   0.5      4      50      78.1632     78.1632
   1.0      4      50      78.1632     78.1632
   1.5      4      46      78.1632     78.1632
   2.0      4      37      78.1632     78.1632   ← 指令が35%減っても小数4桁まで同一
```

**ARS を 35% 多く回しても、水は1滴も減らない。**
機構は素直で、コードのとおりである。ARS は水を消費しない。捕集した CO₂ は Sabatier の原料で、
Sabatier は `run_ogs` の中で**水を作る**側にいる。水を消費するのは電気分解だけで、
それは O₂ 需要に紐づいており CO₂ の判断とは独立している。

**したがって「CO₂ を守ると水が減る」という代償は存在しない。**
（EXP-024 が 55本中13本で観測した「ARS 増 → 水が悪化」は、下の乗員経由の効果である。
EXP-024 は現象を正しく記録したが、原因を ARS に帰した点は本 EXP が訂正する。）

## では EXP-024 の観測は何だったのか — 唯一の結合は「乗員の死」

CO₂ の判断と水を結ぶ経路は1本しかない。**水の需要は生存乗員に比例する。**

```
乗員   50 step の水の減り
  4        1.8368 L
  3        1.3535 L      ← 1人減ると 0.4833 L 節約される
  2        0.9425 L
  1        0.4625 L
```

**つまり「早めに1人を CO₂ で死なせると、残りが水で死なずに済む」。**
これは EXP-023 で提案を撤回した「**乗員が死ぬと点が上がる**」と同じ構造である。
違いは、あのときは**採点式**の病理で、今回は**物理**だという点だけである。

## その結合が作る「内点」は、死1人分の幅しかない

掃引3（CO₂ 閾値 × 初期水量 × 故障）で、**この枝で初めて内点が出た**:

```
故障あり・初期水量 52 L
co2_high  0.5  0.8  1.0  1.2  1.5  1.8  2.0  2.5  3.0  4.0
生存乗員    1    1    1    1    3    3    3    3    2    2   ← 両端が中央より悪い
```

**喜ぶ前に幅を測った。** 掃引4（初期水量を 0.25 L 刻みで13点）:

```
50.50 〜 51.50   全滅（10値すべて同一）
51.75, 52.00     ★内点
52.25            飽和（10値すべて同一）
52.50 〜 54.00   端が最良（低い co2_high が最良、EXP-027 と同じ）
```

**窓は 0.5 L。そして乗員1人の死が節約する水が 0.48 L。窓は「死1人分」ちょうどである。**
さらに窓の中でも 1.5 / 1.8 / 2.0 / 2.5 の4値が同点で、**既定値 2.0 がその中に入っている**
＝ 何もしないのが最適。**内点は在るが、そこに測れる判断は無い。**

## 締め方を変えても駄目 — ループが閉じている

案3 をいちばん強い形（水位ではなく**速度**を締める）でも試した。EXP-022 の教訓
「変更を却下する検定は、現状にも全集合にも当てる」に従っている。

```
掃引5  WRS 定格を 13.5 → 0.5 L/day（27分の1）  水位は 77.49 → 73.31 L しか動かず
                                              **生存乗員は 10×10 セルすべて同一**
掃引6  回収不能分だけを上げる                    100本中90本が**質量保存の不変条件で拒否**
                                              （urine + condensate + unrecoverable = potable intake）
掃引7  保存を保った最大の漏れ＝リサイクル全廃     50 step で 80.0 → 73.07 L。**帯の 23.07 L 手前**
掃引8  在庫と速度を両方締める                    内点セルは 1/8 → 0/8 に**減る**
```

**掃引8 が形を教えている。これは勾配どうしの綱引きではなく、崖と崖である。**
乗員は「2 step 連続で帯にいたら1人」で減るので、帯を割るか割らないかの二値になる。
崖と崖の間に内点が出るのは、2つの崖がたまたま隣り合った測度ゼロの帯だけで、
そこは平坦（同点の高原）だから**分解能が無い**。EXP-026 の「1ビットしか測っていない」と同じ形。

## 窓を延ばしても駄目（掃引10）

「50 step が短すぎるだけではないか」を確かめた。**8倍の 400 step まで延ばした:**

```
steps    最小水位L（帯50）   最小O2 kg（致死帯91.31）   最良 co2_high
   50        77.49              103.78                 端（0.5〜1.2）
  400        67.37              102.43                 端（0.5〜1.2）  ← 構造が変わらない
```

平衡の傾きから外挿すると:

```
資源   帯に届くまで      観測窓50 との比
CO2      12 step         窓のほうが4.3倍長い  → 届く
水      950 step         窓の 19分の1        → 届かない
O2     2230 step         窓の 45分の1        → 届かない
```

**理由は「窓が短い」ではなく「ループが閉じている」。**
WRS と OGS が回っている限り、水と O₂ は**減っていく在庫ではなく釣り合っている平衡**で、
窓をいくら延ばしても帯に近づかない。窓の中で帯に届けるのは、在庫上限を持たず
**蓄積する** CO₂ だけである。そして CO₂ の制御は ARS 1本、答えは常に「回す」。

## 同じ壁の5回目。ただし今回は「なぜ」が1つの数字で言える

```
EXP-017 f       撃つのが無料           → 内点が無い
EXP-018 案1     あきらめる側に価値が無い → 内点が無い
EXP-019 案4     曖昧さが無い           → 内点が無い
EXP-027 設計層  切りすぎる罰が無い      → 内点が無い
EXP-028 案3     **拘束される資源が1つしかない** → 内点が無い
```

**これまでの4件は「内点が無い」の言い換えだった。今回はその上流が測れた。**
判断が生まれるには**同じ窓の中で2つ以上の資源が拘束される**必要がある。
この運用点で拘束されるのは CO₂ だけなので、制御は1本、正解は1つ、状況で変わらない。

## R4 に渡す数字 — 漏れは代謝の約5倍でなければならない

案3 が落ちたので、残る道は R4（リーク＋対処手段）だけになる。**その設計入力が出た。**

```
50 step で水を帯（50 L）に届かせるのに必要な sink   43.2 L/day
   乗員4の水スループット合計                        9.12 L/day  → **4.7倍**
50 step で O2 を致死帯（91.31 kg）に届かせる sink   19.5 kg/day
   乗員4の O2 需要                                 3.36 kg/day  → **5.8倍**
```

**既存パラメータは全て乗員代謝に紐づいているので、掃引では到達不能だった**
（掃引6 で不変条件が 90本を拒否したのは、まさにこれを守っている）。
**R4 のリークは既存の定数の値ではなく、代謝に紐づかない新しい項でなければならない。**
これは「パラメータを1つ足す」ではなく「平衡を崩す」という質の違う変更である。

## 訂正

- **EXP-024 の「CO₂ の警報線↓ → ARS 増 → 水が減る」は、原因の帰属が誤り。**
  現象は実在するが、経路は ARS ではなく乗員の死である（乗員固定で水位は完全に同一）。
  EXP-024 の「designer 層には代償がある」という結論は、**この訂正により支持を失う。**
- 本 EXP の掃引で `crew_lost_by_cause` を3キー決め打ちで読み、乗員0なのに死因0と誤読した。
  キーは動的（`water_warning` 等）。**計器ではなく集計コードの誤りだった。**
