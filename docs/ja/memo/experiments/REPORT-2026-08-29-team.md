# 1. 要旨

```
① 「AI はルールベースより上手く運用できるか」    → 3世代測って、できない（★下記の但し書き）
② 「では AI をどこに置けば上手くなるか」          → **この実験環境では、どこにも置けない**
③ 測ろうとして見つかった計器の欠陥               → 累計20件（第3期分は9件）。すべて修正済み
④ 次に必要なのは AI への投資ではなく、実験環境の作り直し → **物理を変えるのでチーム判断が要る**
```

**★ ①の但し書き（本文 2 節で詳述）:** 「no-op とも区別できない」は**撤回しました。**
観測時間 50 step を選んだことと、「最後に何人残ったか」という粗い物差しの産物です。
連続量で測り直すと **AI 腕は no-op に有意に勝ちます**（A軸 +0.245・p=0.000065）。
**ルール腕が AI 腕に有意に優る**という①の結論そのものは無傷です。

**①の負け方が重要です。** AI が最初に装置を動かすタイミングの中央値は **13歩目で、ルール腕と完全に一致**。
違うのはその後で、ルール腕が37歩続けるのに対し AI の中央値は4歩。**気づけるが、続けられない。**

**②が今回の新しい結論です。** 判断を置けそうな場所を4か所検査し、4か所とも
「正解が状況によって変わらない」＝考える余地が無いと判明しました。

**前回報告（2026-08-28）以降の GPU 使用は 4分27秒**です。
4.5時間の測定を3回設計し、3回とも実行前に撤回しました（第5節）。

## 3.1 第3期に見つけて塞いだ欠陥 9件

### ★ いちばん安い抜け道 — 試験時間を短くすると点が上がった

シミュレーションの歩数は採点の分母そのものです（`_score_a` が CO₂ 曝露と O₂/水 の不足を
`帯 × steps` で割る）。ところが歩数は「乱数の種と同じ実行ノブ」として、
**2つある監視のどちらの対象からも外れていました。**

```
何もしない腕を 50歩  →  69.4 / 90
何もしない腕を  2歩  →  86.1 / 90   ← 公表しているルール腕 84.35 を上回る
                        scoring_bar_modified = []  operating_point_modified = []  警告行ゼロ
```

以前に見つかった同種の抜け道（満点 90.000）は設定4箇所の書き換えが必要で警告も出ていました。
**こちらはフラグ1つ・警告なしです。**

### ★ キャビン容積を、採点する側が自由に申告できた

気体の分圧は `nRT/V` なので、容積の申告が全ての規格照合に効きます。
**容積は run のどこにも記録されておらず**、採点時に外から与える数字でした。

```
共通3軸/90 が容積の申告だけで動く幅   全26 run で 15.996〜15.998点
                                     （A軸CO₂ 8点 + B軸CO₂ 8点 の全額）
正直な 388 m³ からの最大利得         +8.12点
入力検証も無かった                    -5 m³ が通り B軸が満点。0 は黙って 388 に戻る
```

run 自身が容積を名乗るようにし（`plant_sim.habitat.volume_m3`）、**それを書き換えた run は
両方の物差しで採点を拒否**します。

### ★ 棄却理由が記録されていなかった

AI の提案の8割が「不正」として捨てられていましたが、残るのは
**`invalid payload for set_parameter` という理由なしの1行だけ**。
提案の中身も、AI の回答本文（probe では9,000字超）も破棄されていました。
さらに**全件棄却された run はファイルごと作られず**、集計から消えていました。

### ★ designer に「乗員」の存在を伝えていなかった

設計提案を出す AI に渡していたのは、気体の量・指令回数・装置の状態だけ。

**目的を伝えないまま「救えなかったね」と採点していた**ことになります。

## 3.2 手順として取り入れたこと

**独立監査を制度化しました。** 観点の違う監査（検証／破る／事前登録の査読）を3体、
**互いの結論を知らせずに並列**で走らせ、それぞれに次を明示して渡します。

```
・著者は自分を騙していると仮定せよ
・その回の偏りの向き（著者が何を望んでいる状態か）
・自己申告した弱点の一覧（その先を狙わせるため）
・読み取り専用の制約と、GPU を使わせない指示
```

**指摘は全件こちらのコマンドで再現してから採用**します。再現しなかったものは「再現しなかった」と記録します。
第3期は3巡実施し、**判断を変える指摘が毎回出ました**。

# 4. 新しく取り入れた規律（今回いちばん効いたもの）

```
1  設計文書を書く前に、**その問題が定数で解けないか**を見る
   費用: 数分・GPU 0秒。これで EXP-027 の実験が不要と分かった
2  主指標を決めたら、測る前に**判断ゼロの入力**を通す
   費用: 30秒・無料。定数1行が10問中10問正解になり、指標の故障が分かった
3  検定は**現状にも、全集合にも**当てる
   片側だけ／一部の集合だけに当てると、当てた側が有利に見える
4  部分集合の平均を全体の代表として引かない
   このセッションで3回やった（うち1回は報告前に自分で気づいた）
5  予測・判定規則・**撤回条件**を測定前にコミットする
   第3期で**事前登録が初めて仕事をした** — 撤回条件を先に書いていたので、
   指摘を受けたときに解釈で押し切る余地が無く、判断が自動になった
```

# 5. 撤回したこと（3件・すべて実行前）

**4.5時間の GPU 測定を3回設計し、3回とも実行前に撤回しました。**

### 撤回1 — 前提の誤り

「酸素の合格ラインが、提案側から書き換えられる場所にある」という前提で改修を計画しましたが、
**採点が読んでいるのは別の場所**で、そちらは既に保護されていました。
移していれば、**保護のある場所から無い場所へ動かす**ことになっていました。

### 撤回2 — 自分の統計ミス

「合格ラインを変えても 0.075点しか動かないから不要」と書きましたが、**実際は 0.346点**でした。
集計から run が1本落ちており、しかもそれは**まさにこの変更が拾うべき run**
（乗員は生きたが酸素が壊滅的だった run）でした。**監査3体のうち2体が独立に指摘。**

### 撤回3 — 物差しの故障

AI の設計能力を測る実験を組みましたが、その主指標が
**「run を一切読まない定数1行で10問中10問正解」**になりました。

```
{"change_kind":"set_parameter","payload":{"target":"thresholds.co2_storage_high_kg","value":1.8}}
→ 集合A 10本すべてで乗員救出（判断ゼロ）
```

さらに、**AI が回答を書き損ねるとプログラムがルールの正解を代筆する**仕組みがあり、その代筆も
10/10 救出します。**AI の完全な失敗が「棄却0%・正しい提案・乗員救出」として記録される**状態でした。

## 判断4 ★ `request_o2` をどうするか（**新規・実バグを含みます**）

**AI 腕だけが押せる「押すと必ず損をするボタン」があります。**

`request_o2` は名前のとおり「酸素を要求する」指令ですが、いまのシミュレータでは
**キャビンから酸素を抜いて、集計欄に足すだけ**です。抜いた酸素はどこにも行きません
（物理整合ゲートも「損失」として扱っています）。**乗員はそのキャビンの酸素を吸っています。**

```
AI へのプロンプト   このコマンドを**明示的に提示**しています
ルール腕            **コードに分岐が無く、構造上このコマンドを出せません**
実害                3世代で13本の AI run がこれを使い、O2 が原因の死は
                   使用群 2.08人/本 対 未使用群 0.24人/本（**8.8倍**）
```

### ★ そしてこちらは実バグです

**「拒否された」と記録された指令でも、酸素は抜けています。**

```
v3 llm_r12 step22
  operational_rejected  request_o2 amount=10.0  success=False
  実際に抜けた量 8.61 kg（在庫 8.64 kg のほぼ全部）
  酸素 8.643 → 0.0 → 同 step に3人死亡
```

`plant_sim` は**払い出してから成功判定**しています。一方 `loop_mock_backend.py` は
コメントで *"All-or-nothing like SSOS `/ogs/request_o2`: reject without mutating"*
と書いており、**2つのバックエンドで契約が食い違っています。**

**したがって「バックエンドで拒否する」という対策は、現行の実装では効きません。**

### 判断していただきたいこと

```
A どちらのバックエンドが正しいか（払い出してから判定 / 拒否したら何もしない）
   → SSOS 実機の /ogs/request_o2 がどちらかで決まります。**この枝には分かりません**
B AI へのプロンプトから request_o2 を外すか
   → 外せば AI 腕とルール腕の「使える手」が揃います。
     ただし**実機に存在するサービスを隠す**ことになります
C 名前を変えるか
   → 「要求」ではなく「排出」なら、AI が罠にかかりにくくなります。
     ただし実機のサービス名と食い違います
```

**この枝の意見:** A は実機の仕様なので**チーム（または上流）にしか決められません**。

> ### ⚠ 追記（2026-08-29）— この枝は**矛盾のほうだけ**を直しました
>
> **A は決めていません。** 決めたのは「**この repo の2つのバックエンドが食い違っていること**」だけで、
> そちらは実機の仕様を待たずに判定できます。
>
> ```
> 直した内容  plant_sim の request_o2 / request_co2 / request_product_water を
>            **抜く前に判定する**（在庫不足なら何も動かさずに拒否）。
>            合わせ先は、同じ repo が名指しで書いている契約 —
>            loop_mock_backend「All-or-nothing like SSOS /ogs/request_o2」
> 影響       **公表値は不変**（82.2297 / 68.6661）。ルール腕は request_* を構造上出さないため。
>            既存 run の再採点も不変（telemetry は固定）。テスト 642 → **646 passed**
>            ⚠ ただし**今後 LLM 腕を回すと、過大要求を出した run は v5 と比較できません**
> 元に戻す   **1コミットです。** A が「払い出してから判定が正しい」と決まれば revert します
> ```
>
> **B（プロンプトから外す）と C（名前を変える）は、引き続き判断をお願いします。**
> どちらも実機との対応に関わるので、この枝では触っていません。
まず A を確定させ、そのうえで B・C を考えるのが順序だと思います。

**なお、これは「AI が下手」という話ではありません。** 罠を使った13本を除くと、
**AI 腕は「何もしない腕」より有意に良い**（死を遅らせ、CO₂ を低く保つ）ことが分かりました
（下の「AI 腕は中間だった」を参照）。
