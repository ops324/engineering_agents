## 何をしようとしていたか

[EXP-026](EXP-026-the-metric-a-constant-string-wins.md) の指摘を全て直したうえで、
LLM designer の実験を設計し直すつもりだった。監査が「集合A は天井なので、
ルールが救えなかった run（集合B）を足せば『量』の判断に分解能が出る」と指摘していたので、
**設計を書く前にその前提を確かめた。**

## 前提は半分正しく、半分間違っていた

### 正しかった — ルールは 27本ぶん取りこぼしている

exp019 で乗員を失った run は **43本**。ルールの designer が救えたのは 10本だけ。
残り 33本に、**警報線をもっと深く切る提案**を当てた:

```
thresholds.co2_storage_high_kg = 1.8（ルールの刻み ＝ 2.0 × 0.9）  → 救出  0/33
                                 1.0                              → 救出 **27/33**
                                 0.5                              → 救出   27/33
```

**ルールの真の天井は 10/43 で、定数 1.0 なら 37/43 である。**
取りこぼしの原因は「どのレバーか」ではなく「どれだけ引くか」— **刻みが ×0.9 で固定だから。**

### 間違っていた — そこに判断は置けない

**1.0 と 0.5 は、全指標で完全に同一だった。**

```
値     peak_kg   終端余裕   water_min   o2_min   曝露積分   帯超過step
1.8   -0.0932   +0.1595    +0.0365   +0.0021   -0.0288    -0.0606
1.0   -0.5270   +0.2667    -0.1532   -0.0137   -0.2102    -0.3636
0.5   -0.5270   +0.2667    -0.1532   -0.0137   -0.2102    -0.3636   ← 1.0 と1桁も違わない
```

**機構は飽和である。** 治療腕の ARS 指令数を比べた:

```
end15  1.8→30  1.0→45  0.5→45        end18  1.8→33  1.0→42  0.5→42
end16  1.8→33  1.0→44  0.5→44        end19  1.8→32  1.0→41  0.5→41
end17  1.8→34  1.0→43  0.5→43        end20  1.8→31  1.0→40  0.5→40

1.0 と 0.5 で ARS 指令数が同一な run: **33/33**
```

警報線がある値より下がると、**ARS は定格が許すかぎり毎 step 発火し、それ以上は下げても何も変わらない。**
[定格の不変条件](../ssos_eclss_loop/rated_capacity_invariant.md)が、設計の層に現れている。

## 結論 — 同じ壁の4回目。今度は設計の層で

```
EXP-017  f（判断点）      撃つのが無料 → 常に撃つのが最適 → 内点が無い
EXP-018  案1（指令の上限） あきらめる側に価値が無い → 内点が無い
EXP-019  案4（修理と診断） 署名に曖昧さが無い → すぐ直すが支配的 → 内点が無い
EXP-027  設計の層         **切りすぎる罰が無い → 定数が最適 → 内点が無い**
```

**「量を選ぶ」を LLM に渡す実験（EXP-025 の腕3）は成立しない。**
`{"target":"thresholds.co2_storage_high_kg","value":1.0}` という**定数1行が、
ルールの designer を 27本ぶん上回る。** 判断が要らない。

**そして EXP-026 が示したとおり、救出はこの定数で満点になる。**
主指標を「有効提案率」に替えても同じで、**定数1行の有効提案率は 100% である**
（1件出して1件効く。ルールは 309件出して 55件＝17.8%）。

## それでも残る、AI と無関係な発見

**ルールの designer は、刻みが ×0.9 固定なせいで 27本の救出を取りこぼしている。**
これは AI の話ではなく、**ルールの designer 自身の欠陥**である。

```
現在      new = old × 0.9        → 43本中 10本を救う
定数 1.0  値を飽和点まで下げる    → 43本中 37本を救う
```

**ただし「1.0 に下げる」が正しい設計かは別問題である。**
飽和点まで下げるとは「CO₂ 警報を実質的に鳴りっぱなしにする」ことで、
それが良い運用かどうかは、この枝が単独で決めることではない（R3 の領域）。
**測定として言えるのは「いまの刻みでは救えるものを救っていない」ことだけ。**

---

## R6 への含意

**「AI をどこに置けば上手くなるか」の答えは、この運用点では「どこにも置けない」である。**

- actor の層に判断点が無い（EXP-017・018・019）
- 設計の層にも無い（本 EXP）
- 効くレバーは1本で、その最適値は定数で、飽和している

**退化は腕の性質ではなく運用点の性質であり、層を上がっても消えない。**

**したがって次に払うべきは LLM ではなく、運用点である:**

```
案3   水のために運用点を締める（世代 v6・全 run 比較不能）
R4    リーク ＋ 対処手段（物理変更。診断が初めて判断になる）
```

**どちらも物理を変える。それが、判断を置く場所を作る唯一の残った道である。**

EXP-025 は2版とも、**任務が定数で解けることを確かめずに**書かれていた。
確かめるのに要ったのは `ea evaluate` 約200本、**GPU 0秒、数分**である。

**EXP-026 の教訓（主指標に判断ゼロの入力を通す）の一段手前に、これがある:**
**主指標を選ぶ前に、任務そのものが定数で解けないかを見る。**
