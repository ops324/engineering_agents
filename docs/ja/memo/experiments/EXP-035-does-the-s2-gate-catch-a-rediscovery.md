## ★ この測定が壊れる最大の理由（先に書く）

**答えを知っている人間が、答えを知った後に作った索引に、答えを知っている質問を当てれば、
捕捉率は必ず 100% になる。** EXP-026 の「run を一切読まない定数1行が救出 10/10」と同じ型で、
**指標が判断を測っていない**状態である。防具を3つ置く。

```
防具1  クエリを著者が書かない  会話ログ 13cd226b.jsonl の**初稿を verbatim** で使う。
                            初稿は「既出だ」と気づく前に書かれており、行番号と時刻で固定した
防具2  コーパスを時刻で切る    各クエリの初稿が書かれた時刻より前の記録だけを索引する
防具3  偽陽性を必ず対で出す    捕捉率だけの報告を禁じる。定数腕（常に「既出」）は捕捉 3/3 になる
```

**安い腕が失敗した理由は、機構まで分かった:**

```
Q1（取り逃し）  初稿と既出先が数値を1つも共有しない。初稿は +0.245 も +0.246 も書いていない。
               再発見は**意味の一致**であって数値の一致ではなかった
Q3（数値grep失敗） 既出先の数値は「4, 5, 6, 6, 7 ...」という**整数**。小数リテラルに掛からない
               しかも数値grep の1位は `ccda5e5` ＝ **別件（Q2）の既出先**を返した
Q2（TF-IDF失敗） 順位 9位。同じ日の STATE.md と報告書が上位を占めて押し出した
```

**⇒ 数値で見つかる再発見と、文章で見つかる再発見は別物で、どちらの安い腕も片方しか取れない。**

## ★★ いちばん重い発見は、私の事前登録そのものが壊れていたこと

**撤回条件1「実用腕が腕0 を recall と偽陽性の両方で上回れないなら棄却」は、原理的に到達不能だった。**
定数腕の recall は 3/3 で上限であり、**どの腕も「上回る」ことは構造上できない。**

**これは [EXP-023](EXP-023-the-rule-i-wrote-fired.md) の「基準2 破綻 — p<0.01 は原理的に到達不能」と同じ型である。**
6日前に一度踏んだ落とし穴を、**それを防ぐために書いた事前登録の中で再現した。**

```
正しい書き方   「腕0 に支配されないこと」＝ 偽陽性で厳密に上回り、recall で下回りすぎないこと
             ＝ 定数との差を**2軸の同時比較**で書く。単軸の「上回る」は定数相手には書けない
```
**この条件は棄却の判断に使わない。** 上の表を、腕0 との2軸比較としてそのまま読む。
