## なぜ、いま測る価値があるか

[EXP-024](EXP-024-the-loop-nobody-ran.md) が**基準線を取った。** それまでは
「LLM designer は improved を出した」としか言えず、それは何も意味しなかった。

**ルールの designer（71本・決定的・無料）:**

```
verdict        improved 38 / mixed 17 / no_effect 16
効くレバー      thresholds.co2_storage_high_kg ただ1本
無効な提案      309件中 190件（action_profile 125 + service_config 65）が全て空振り
乗員救出        10本で 3/4 → 4/4（12.5点）。**全て故障注入下**
```

**問いが3つに定まった:**

```
① 無効なレバーを避けられるか（ルールは 61.5% が無駄撃ち）
② 効くレバーを、より適切な量で引けるか
③ ルールが何も見つけられなかった run で、何か見つけられるか
```

## 設計 — 交絡が無い比較になる

**actor を `labeled_rule_base`（決定的）に固定し、designer だけを差し替える。**

```
対照  actor=labeled_rule_base  designer=labeled_rule_base   ← EXP-024 で測定済み
処置  actor=labeled_rule_base  designer=llm(27B)            ← 今回
```

**軌跡は両腕で完全に同一である**（actor が決定的なので）。
したがって designer は**同じ入力**を見る。**差は designer だけ。**

これは EXP-015 の交絡（actor 9B 対 design 27B の非対称）を**持たない** —
今回は actor が LLM ではないので、モデルサイズの非対称が入る余地が無い。

### 対象とする集合

```
集合A（判別・n=10）  ルールの designer が乗員を救った10本
                     end14 / f_m0.4 / m0.0_e14 / m0.15_e14 / m0.15_e15 / m0.15_e16 /
                     m0.3_e16 / m0.3_e17 / m0.3_e18 / m0.3_e19
                     問い: **LLM も救えるか**
集合B（対照・n=8）   ルールの designer が no_effect だった run の**全部**
                     f_m0.8 / f_m1.0 / m0.15_e11 / m0.15_e12 /
                     m0.3_e11 / m0.3_e12 / m0.3_e13 / m0.3_e14
                     問い: **ルールが見落としたものを見つけられるか**
```

**集合B は「選んでいない」。** exp019 の no_effect は8本しか無く、その全部を使う。
**選択の余地が無いので、選び方が結果を作ることはない**（下の W5 はこれで解消した）。
集合A も同様に「ルールが救えた run の全部」であり、両方とも悉皆である。

**LLM は seed を固定しても再現しない**（[EXP-012](EXP-012-noise-floor.md)）ので、
各シナリオ **3 repeats**。合計 **(10 + 8) × 3 = 54 designer run**。

### 手順

```
1. 各シナリオを actor=labeled_rule_base + design-mode=llm で走らせる（軌跡は既知と同一）
2. 生成された design_proposals.json を ea evaluate にかける（対照/処置とも決定的・無料）
3. 集合A の救出率、集合B の改善率、repeats 間のばらつきを数える
```

## 予測（測定前にコミットする。判定規則も併記）

**この枝は予測を後から書いて4回撤回した。今回も先に書く。**

```
P1  集合A で、LLM designer の救出率はルールを下回る（ルールは 10/10）
    判定: 30試行（10シナリオ×3）のうち救出した数。**28以上なら P1 は外れ**

P2  集合B で、LLM designer はルールが見落としたものを**ほとんど見つけない**
    判定: 24試行（8シナリオ×3）のうち improved または乗員救出が出た数。
    **3以上なら P2 は外れ**

P3  同じシナリオの 3 repeats で、verdict のラベルが揃わない（一貫性の問題が
    designer 層でも再現する）
    判定: 18シナリオのうち3本とも同じラベルだったものの割合。**50%以上なら P3 は外れ**

P4  LLM の提案には、スキーマ違反または許可外ターゲットが含まれる
    （ルールは構成上ゼロ）
    判定: parse_notes または validate の拒否が出た試行数。**0 なら P4 は外れ**
```

## 解釈規則（これも先に書く）

```
P1 かつ P2 が当たる → **判断点 d でも LLM はルールに劣る。**
                      「AI をどこに置くか」の答えは、d でも「置かない」になる
                      3世代（actor 層）＋1（designer 層）で同じ結論
P2 が外れる         → **これがいちばん面白い結果。** ルールが見落とした改善を
                      LLM が見つけたことになる。**その場合、次は「何を見つけたか」を読む**
P3 が当たる         → 失敗の型が actor 層と同じ（能力ではなく一貫性）。
                      **2層で同じ型なら、それは腕の性質ではなく LLM の性質である**
P1 が外れる         → LLM がルールと同等以上に救えた。**ハイブリッドの根拠になる**
```

**⚠ 主指標は「乗員救出」にする。** `ea evaluate` の verdict は
[EXP-024 結果3](EXP-024-the-loop-nobody-ran.md) のとおり9指標を等重みで数え、
**人を1人救った提案を全て `mixed` と判定する。** 主指標に使えない。
verdict は副次的に記録するだけにする。**この判定は EXP-024 の観察に基づき、
本 EXP のために新設した指標ではない。**

## probe（1本・実測済み・費用の確定のため）

**⚠ n=1。実験ではない。** 予測 P1〜P4 はこの probe の出力が存在する前に書かれている
（設計文書 04:23:43、probe 出力 04:25:18。タイムスタンプで確認可能）。

```
所要        4分27秒（うち約1.5分が simulation、残りが designer）
提案        14件のうち **11件が payload 不正で棄却**（set_parameter 8 / action_profile 3）
通った3件   graph_rewire 1 + service_config 2
            → **どちらも EXP-024 が「100% 無効」と測定した種類**
thresholds  **ゼロ件**（＝EXP-024 が「唯一効く」と測定したレバーを引いていない）
verdict     no_effect（全9指標が完全に不変）
```

**P4（スキーマ違反が出る）は n=1 で既に成立している。** P1・P2 も同じ向きを示すが、**1本では何も言えない。**

### ★ probe が、実験より先に本物の欠陥を見つけた

`ea evaluate` の対照/処置腕が、**baseline の `agents.design.mode` を継承して designer を再実行していた。**

```
designer は run の後に動くので軌跡に影響しない
腕が出した提案は書かれるだけで読まれない（試験対象は baseline の提案）
＝ 純粋な無駄。design.mode: llm なら **1 repeat あたり 27B を2回**
実測: 修正前 9分超（タイムアウト）→ 修正後 **0.4秒**
```

**この欠陥が残っていれば、EXP-025 の費用は 4時間ではなく約12時間だった。**
数字は1つも変わらない（既存3本で verdict・delta とも一致を確認）。
修正済み。テストを追加した。

**probe を撃たずに設計文書を承認していたら、3倍の請求書に気づかなかった。**
