## ★ 撤回のきっかけ — probe が「何を測ることになるか」を示した

**LLM designer は、何を変えてよいかを一度も教えられていない。**

probe（n=1）で棄却された提案の中身:

```
LLM が提案した     eclss.o2.hysteresis_kg / eclss.water.hysteresis_l   ← 書式は正しい
実際に動かせるのは  thresholds.* と agents.actor.policy.*（ALLOWED_SET_PARAMETER_TARGETS）
結果               14件中 11件を検証器が黙って棄却（79%）
```

プロンプト（`src/scenario/agents/ssos_post_run_design.py:291-331`）を読んだ:

```
渡している    初期条件 / テレメトリ要約 / 世界状態 / actor 最終状態 / 会話 / baseline グラフ
              thresholds は「Verification requirement stubs (context only)」＝参考情報のみ
渡していない  ★ ALLOWED_SET_PARAMETER_TARGETS（何を変えてよいか）
              ★ どの change_kind が実際に効くか（EXP-024 で判明済み）
```

**第1版の設計は、「LLM がうちのパラメータ名を当てられるか」を 54回・4時間かけて測るものだった。**
そして結果を「LLM は designer としても劣る」と読むところだった。

**これは能力の測定ではなく、合成の失敗の測定である。**

## 設計 — 判断点を1つずつ渡す梯子

designer の仕事は4つに分かれる。**ルールで固定する部分と LLM に渡す部分を、1段ずつ動かす。**

```
                     1診断   2レバー選択          3量     4書式    状態
腕0 ルール           ルール   ルール               ルール  ルール   ✅ 測定済（EXP-024・71本）
腕1 現状の LLM       LLM     LLM（選択肢を知らない） LLM    LLM     n=1（probe・79%棄却）
腕2 選択肢を渡す      LLM     LLM（選択肢を渡す）    LLM    ルール   ← **今回測る**
腕3 レバーを固定      LLM     ルール（thresholds）   LLM    ルール   ← 第2段階（条件付き）
```

**測るのは「ハイブリッドが勝つか」ではなく「どの判断点を渡すと効き、どこで害になるか」である。**

### 第1段階（今回）— 腕1 と 腕2 を比べる

**問い: 「何を変えてよいか」を教えると、AI の提案は変わるか。**

```
対象      集合A（ルールが乗員を救った10本の全部）
repeats   3（LLM は seed 固定でも再現しない・EXP-012）
腕        腕1（現状のプロンプト）と 腕2（選択肢を渡すプロンプト）
合計      10 x 3 x 2 = **60 run ≈ 4.5時間**
```

**腕1 を n=1 のままにしない。** probe が偶然だった可能性を潰すため、腕1 も 30 run 走らせる。
**片方だけ全集合に当てるのは EXP-023 で落ちた形である。**

### 腕2 の実装（②の判断が下りてから）

プロンプトに次を足す。**それだけ。** 採点式にも物理にも触らない。

```
1 set_parameter の許可ターゲット一覧（ALLOWED_SET_PARAMETER_TARGETS の10件）
2 change_kind ごとのスキーマ（payload の形）
3 ★ 何も足さない: 「どの change_kind が効くか」は渡さない
```

**3 が重要である。** EXP-024 は「効くのは `thresholds.co2_storage_high_kg` だけ」と測ったが、
**それを教えてしまうと答えを渡すことになり、測っているのは AI ではなく私になる。**
渡すのは**行動空間**であって、**正解**ではない。

## 予測（測定前にコミットする。判定規則も併記）

```
P1  腕2 の棄却率は腕1 より大きく下がる
    判定: 提案件数に対する parse_notes の割合。腕1 は probe で 79%。
    **腕2 が 20% を下回らなければ P1 は外れ**

P2  腕2 は thresholds.* を提案するようになる
    判定: thresholds.* を含む run の割合。腕1 は probe で 0/1。
    **腕2 が 50% を下回れば P2 は外れ**

P3  それでも腕2 の救出率は、ルール（集合A で 10/10）に届かない
    判定: 30試行のうち救出した数。**28以上なら P3 は外れ**

P4  腕1 の棄却率は probe（79%）と同水準で、probe は偶然ではない
    判定: 30試行の平均棄却率。**50% を下回れば P4 は外れ**
```

## 解釈規則（先に書く）

```
P1・P2 が当たり P3 も当たる
  → **AI は行動空間を教えれば使えるが、それでもルールには届かない。**
    次は腕3（レバーを固定して量だけ渡す）。判断点をさらに絞る
P1・P2 が当たり **P3 が外れる**
  → **これがいちばん重い結果。** 失敗は能力ではなく合成だったことになる。
    「AI をどこに置けば上手くなるか」に初めて肯定的な答えが出る
P1 が外れる
  → 選択肢を渡しても棄却率が下がらない。**別の原因がある。GPU を止めて診断する**
    （腕3 に進まない。金を払う前に理由を知る）
P4 が外れる
  → probe が偶然だった。第1版の撤回理由の一部が崩れる。**その場合は撤回自体を見直す**
```

**主指標は「乗員救出」と「棄却率」。** `ea evaluate` の verdict は
[EXP-024 結果3](EXP-024-the-loop-nobody-ran.md) のとおり、人を1人救った提案を全て `mixed`
と判定するので主指標に使えない。副次的に記録するだけにする。

## probe（n=1・費用の確定のため実行済み）

**新しい P1〜P4 は、probe を読んだ後に書いている。第1版の予測は撤回した。そこは隠さない。**

```
所要        4分27秒（うち約1.5分が simulation）
提案        14件中 11件が棄却（set_parameter 8 / action_profile 3）
通った3件   graph_rewire 1 + service_config 2 ← どちらも EXP-024 が「100%無効」と測定した種類
thresholds  ゼロ件
verdict     no_effect（全9指標が完全に不変）
```

### ★ probe が、実験より先に本物の欠陥を見つけた

`ea evaluate` の対照/処置腕が、baseline の `agents.design.mode` を継承して
**designer を再実行していた。** designer は run 後に動くので軌跡に影響せず、腕が出した提案は
読まれない。**純粋な無駄。**

```
実測  修正前 9分超（タイムアウト）→ 修正後 0.4秒   （`899bb3c` で修正・テスト追加）
```

**残っていれば第1段階の費用は 4.5時間ではなく約13時間だった。**
数字は1つも変わらない（既存3本で verdict・delta とも一致を確認）。

## この測定がしないこと

- 採点式の変更（1文字も変えない）
- 物理の変更（無し）
- actor を LLM にすること（交絡の無さは actor が決定的であることに依存する）
- **EXP-024 の答え（効くレバーは thresholds だけ）を LLM に教えること**

## 手戻り

**採点・物理は不変。** 変わるのは designer のプロンプトだけで、既存 run は全て有効なまま。

## 着手前にやること

**原則4 の独立監査。** 発動条件のうち4つに当てはまる:
GPU を払う／設計・物差し・予測が同じ手から出ている／**著者は第1版を撤回した直後で、
今度は逆向きに偏っている可能性がある（W6）**／**主指標の1つを probe を見た後に選んだ（W7）**。
